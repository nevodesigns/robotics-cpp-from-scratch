id: E-QT-0015
title: deleteLater in a test, and an object that is still there
match: deleteLater deletes nothing, and processEvents does not either
platforms: linux, windows
teaches: 09-04-who-deletes-this
---

## Symptom

A test calls `deleteLater`, pumps the event loop with `processEvents`, and
asserts the object is gone. It is not. A leak check reports the object still
alive at the end of the run, or a destructor that should have released a port or
closed a file never runs.

In the application it works, which makes it look like a test problem rather than
a real one.

## Cause

`deleteLater` does not delete anything. It posts an event, and the event is only
acted on when an event loop reaches it.

`processEvents` does not reach it. Deferred deletions are held back from
`processEvents` deliberately, so that an object cannot be destroyed while a
nested loop is still executing inside one of its own member functions. That is
the right decision and it is not obvious.

Measured, on one object that has had `deleteLater()` called:

| | alive |
|---|---|
| after `deleteLater` | 1 |
| after `processEvents` | **1** |
| after `sendPostedEvents(nullptr, QEvent::DeferredDelete)` | 0 |

In an application it works because the main event loop returns to the top and
runs them. A test usually has no loop at all, so the deletion is posted and
nothing ever collects it.

## Fix

Run them explicitly, in one named place.

```cpp
inline void drain_deferred_deletes(QObject* only = nullptr) {
  QCoreApplication::sendPostedEvents(only, QEvent::DeferredDelete);
}
```

Then a test reads as what it means:

```cpp
object->deleteLater();
RC_CHECK(still_alive(watching));   // nothing yet
rc::qt::drain_deferred_deletes();
RC_CHECK(!still_alive(watching));  // now
```

Two things that go with it.

**Check with a `QPointer`, not a counter alone.** A counter says how many exist;
a `QPointer` says whether this one does, and it is the only way to ask about an
object somebody else owns. See `E-QT-0016`.

**Do not reach for `delete` instead.** `deleteLater` exists because deleting an
object while it is inside one of its own slots, or from another thread, is the
bug it prevents. The fix is to run the deletions, not to stop deferring them:
see `E-QT-0017`.

And in an application, remember that an object with `deleteLater` pending is
still alive and still connected. It will receive signals in the meantime, and a
slot that assumes it is on its way out has to say so itself.
