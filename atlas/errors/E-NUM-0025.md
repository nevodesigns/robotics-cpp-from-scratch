## Symptom

A pose is saved and loaded and the robot ends up slightly somewhere else. A
comparison between a value and the same value read from a file fails. A replay
of a recorded run drifts away from the run it recorded, by an amount that
grows.

Nothing is wrong with the numbers in memory. They were wrong the moment they
were written.

## Cause

A stream writes a `double` with six significant digits unless told otherwise.

Measured on 200 values a robot actually has, a running sum of `0.1` and square
roots, written as text and read back: **21** came back identical with the
default, and **200** with `rc::core::exact_text`.

Two numbers are worth knowing.

| | |
|---|---|
| `digits10` | **15**. A decimal this long survives being a double. |
| `max_digits10` | **17**. A double this long survives being a decimal. |

So a value a person typed, `2.45`, survives with 15 digits and comes back as
`2.45`. A value the program computed may need all 17. Measured:
`0.1 + 0.2` is `0.30000000000000004`, and 16 digits give a different double.

## Fix

Write as many digits as the value needs and no more.

```cpp
#include <rc/core/save.hpp>

rc::core::exact_text(0.1);          // "0.1"
rc::core::exact_text(0.1 + 0.2);    // "0.30000000000000004"
rc::core::exact_text(100.0);        // "100"
```

Not 17 digits everywhere. That is always correct and writes `0.1` as
`0.10000000000000001`, which nobody can read and nothing can diff.

`nan`, `inf` and `-inf` are written as those words. The reader from lesson
01-12 refuses all three and counts them, which is the right outcome: a value
that is not a number should be reported, not turned into one.

One caution. This depends on the program's locale writing a point and not a
comma for the decimal separator. In the default `"C"` locale it does.
