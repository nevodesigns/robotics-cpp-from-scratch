## Symptom

A crash inside Qt, in a call stack with none of your functions near the top. Or
a slot that reads a member of an object that no longer exists and gets whatever
is in that memory now: plausible numbers, occasionally.

It happens when a window closes, or a device is unplugged, or a mode changes,
and it is hard to reproduce because the memory is usually still readable.

## Cause

A raw pointer to a destroyed `QObject` holds an address that used to mean
something, and there is no way to ask it whether it still does.

Qt's ownership makes this easy to arrive at without noticing. A parent destroys
its children, so anything holding a pointer to a child has that pointer
invalidated by a `delete` somewhere else entirely:

```cpp
Counted* parent = new Counted();
Counted* child = new Counted(parent);
delete parent;        // the child went too
```

And reparenting moves the responsibility. A child given to a new parent survives
the old one:

| | first parent's children | second's | alive |
|---|---|---|---|
| after construction | 1 | 0 | 3 |
| after `setParent(second)` | 0 | 1 | 3 |
| after `delete first` | | 1 | **2** |

So "who deletes this" is a question whose answer can change at runtime, and the
holder of a raw pointer is not told either way.

## Fix

Hold a `QPointer` to anything you do not own.

```cpp
QPointer<Counted> watching(object);
// ... somebody else may destroy it
if (!watching.isNull()) watching->use();
```

A `QPointer` is told when its object is destroyed and becomes null. That is the
whole of it, and it is the only way to hold a reference to something owned
elsewhere and still be able to check.

It is the same idea as the `weak_ptr` in lesson 02-06, arrived at from the other
direction. There, ownership is shared and a weak reference declines to extend
it. Here, ownership belongs to a parent and a `QPointer` declines to pretend
otherwise.

Three habits that go with it.

**Say who owns each object, in a comment, where it is created.** A parent, a
`unique_ptr`, or a container: one of the three, named.

**Prefer a parent to a raw `new` with no owner.** An object with no parent and
no other owner is a leak the moment somebody forgets it, and Qt gives you the
tree for free.

**Never give a stack object a parent.** Its destructor runs at the closing brace
whatever Qt believes, and the parent then deletes it again. A child deleted
first removes itself from the parent's list, which is why deleting a heap child
early is safe and this is not.
