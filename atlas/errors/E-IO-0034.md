title: The answer to the question before
match: a response to another request is stale, is counted, and does not complete this one
match: a late answer to a request given up on is not the answer to the next one
match: expected ids.wrong to equal
platforms: linux, windows

## Symptom

A command is acted on with the wrong result. The robot reports the position it was
at a moment ago, or the voltage from the previous reading, or the answer to a
different question, and then, a moment later, the right one. Sometimes every
answer is one request behind for a while, and then it corrects itself.

Nothing is reported as an error. Every message was valid, every checksum passed.

## Cause

The requester took the next response that arrived as the answer. On a link that can
delay and lose messages, the next response is not necessarily the answer to the
latest request: it can be the answer to one already given up on, and once it has been
taken as the answer to the wrong request the real answer to that request arrives next
and is taken as the answer to the one after. The error **shifts along** the
conversation until a timeout happens to resynchronise it.

Measured, 200 requests to a device that answers one in ten too late and one in
fifteen not at all:

| requester | answered | wrong |
|---|---|---|
| takes the next response | 200 | 49 |
| matches the id | 200 | 0 |

The requester that took the next response also looks the fastest, and resent only
8 times against 27, because a stale answer satisfied it early.

## Fix

A request carries an id, the device copies it into its response, and the requester
accepts only the response with the id it is waiting for. Anything else is counted:

```cpp
if (state_ != RequestState::Waiting || message[1] != id_) {
  ++stale_;
  return true;       // it was a response, so it is dealt with
}
```

`stale()` is worth reporting. A count that climbs says the device is answering late,
which is information the shifted answers were hiding.
