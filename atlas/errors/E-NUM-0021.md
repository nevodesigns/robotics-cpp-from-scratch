id: E-NUM-0021
title: A clock that is accumulated and never reaches the time it was waiting for
match: a time that is accumulated never equals the time you were waiting for
platforms: linux, windows
teaches: 01-08-close-enough
---

## Symptom

A loop that steps a simulated clock by a fixed interval and stops when it
reaches a deadline never stops. Or it stops, and does one iteration more than
arithmetic says it should, so a ten second run logs 101 samples instead of 100
and a trajectory arrives slightly past its end point.

```cpp
double t = 0.0;
while (t != 10.0) { step(); t += 0.1; }
```

## Cause

0.1 has no exact binary form, so every addition carries a small error, and the
errors accumulate.

A hundred additions of 0.1 reach **9.99999999999998046**, which is not 10.0 and
is not above it either. So `t != 10.0` is true forever, and `t < 10.0` is still
true after a hundred steps and takes a hundred and first.

The drift is not a fixed cost. Measured against the exact answer, in
representable doubles:

| steps | error | doubles adrift |
|---|---|---|
| 10 | 1.110e-16 | 1 |
| 1000 | 1.407e-12 | 99 |
| 100000 | 1.885e-08 | 10000 |
| 1000000 | 1.333e-06 | 92000 |

About a tenth of a representable double per step, forever. A robot that runs
for hours accumulates a clock that is measurably not the clock it thinks it is.

## Fix

**Count in integers and multiply.** The step index is exact, so derive the time
from it instead of accumulating:

```cpp
for (int step = 0; step < steps; ++step) {
  const double t = step * dt;     // exact for every step
}
```

Measured, `100 * 0.1` is exactly 10.0, while a hundred additions of 0.1 are
not. This is the fix, and it is simpler than the bug.

**Never wait for a float to equal anything.** Use `>=` for a deadline, or
`rc::core::nearly_equal` when you genuinely mean "the same value". The
accumulated clock above is two representable doubles short of ten, which is the
same as ten for any purpose a robot has, and `nearly_equal` says so.

**If you must accumulate, compensate.** `rc::core::kahan_sum` keeps the part
that did not fit and feeds it back, which removes the drift rather than
reducing it.

**Expect the off by one when you convert.** A loop bounded by an accumulated
float runs one extra time more often than not, and that extra sample is usually
the one that lands outside the trajectory.
