id: E-CPP-0045
title: A std::function in a control loop that allocates
match: a std::function allocates when what it holds will not fit inside it
platforms: linux, windows
teaches: 02-08-behaviour-as-a-value
---

## Symptom

A control loop that calls a stored callback misses its deadline occasionally
and unpredictably. A latency histogram has a tail that does not correspond to
anything the callback does. Replacing the callback with a direct call makes it
go away.

```cpp
std::function<void(const Reading&)> on_reading = [state](const Reading& r) { ... };
```

## Cause

`std::function` erases the type of what it holds, and it has to put that
somewhere. It keeps a small buffer inside itself, and anything that does not
fit goes on the heap.

Measured, storing lambdas that capture an increasing amount of state, with
`sizeof(std::function<std::size_t()>)` of 32:

| bytes captured | allocations to store it |
|---|---|
| 8 | 0 |
| 16 | 0 |
| **17** | **1** |
| 64 | 1 |
| 64, called directly with no std::function | **0** |

The lambda itself never allocates. It is a class with one member per capture,
and 64 bytes of captures is a 64 byte object on the stack. The allocation comes
from `std::function` needing somewhere to keep an object whose size it does not
know until runtime.

The size it will hold for free is a standard library choice and not a rule, so
measure it on your toolchain rather than quoting 16.

This bites twice when the capture is a container. Measured on two callables
from lesson 02-08: one capturing a single double cost **0** allocations to
store, and one capturing a whole `std::vector` cost **3**, because the vector
was copied into the lambda and then the lambda was too big to live inside the
`std::function`.

## Fix

**Call it directly when you can.** A callback passed as a template parameter,
or a lambda called where it was written, has no type erasure and no allocation.
The standard algorithms take their callables this way for exactly this reason.

**Keep the capture small when you cannot.** Capture a pointer to the state
rather than the state, after answering the lifetime question that raises.
Eight bytes always fits.

**Construct it outside the loop.** The allocation happens when the
`std::function` is assigned, not when it is called, so building the callback
once at setup and calling it a thousand times costs one allocation rather than
a thousand. A loop that reassigns a `std::function` every cycle is the version
that hurts.

**Count the allocations rather than reasoning about them.**
`rc::test::AllocationCount` from lesson 02-02 turns this into an assertion, and
a loop that must not allocate should have one.

**Reach for a plain function pointer when there is no state.** A captureless
lambda converts to one, which lesson 02-08 measures, and a function pointer
holds nothing and allocates never.
