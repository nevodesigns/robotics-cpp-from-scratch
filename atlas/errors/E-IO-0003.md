title: One read is not one message
match: the same frame is found however the stream is split
match: noise before a frame is discarded
platforms: linux, windows
teaches: 08-02-framing-a-stream

## Symptom

A serial link works on the desk and misbehaves on the robot, in ways that will
not reproduce when you go looking:

- Occasional messages ignored, more often at higher rates.
- A parser that produces nothing at all after the cable is unplugged and
  plugged back in.
- Values that are right most of the time and wildly wrong every few minutes.

The tests pass. They were written by sending a message and reading it back,
which is the one case that always works.

## Cause

The code assumed a read returns a message:

```cpp
std::uint8_t buffer[64];
const int count = port.read(buffer, sizeof(buffer));
handle_message(buffer, count);          // the bug
```

A stream delivers bytes in order. That is the whole promise, and there is
nothing in it about grouping. `read` returns whatever has arrived when you ask,
so it returns half a message when the rest is still in flight, two messages when
both arrived while you were busy, one byte when that is all there was, and a
message with noise in front of it when the link started mid transmission.

None of those is an error condition. Every one is the port working correctly,
and all of them depend on timing, which is why a desk cannot produce them and a
robot can.

The second half of the same mistake is a parser that stops when it meets
something unexpected. In the field the first plugged cable then ends the
session, and the symptom is a link that goes quiet and stays quiet.

## Fix

Frame the messages, and parse a byte at a time.

A frame is a start byte, a length, and that many payload bytes. The start byte
is what a parser resynchronises to, and the length is what lets a payload
contain any byte without escaping.

```cpp
for (int i = 0; i < count; ++i) {
  if (parser.push(buffer[i])) handle_message(parser.payload());
}
```

The parser holds the state between calls, so a message split across two reads is
not a special case, and neither is two messages in one read. A byte at a time
and a thousand at a time go down the same path.

Two properties are worth insisting on.

**It never gives up.** A byte that is not the start byte is discarded, counted,
and the parser keeps looking. Count the discards and report them: a link that
throws away a few bytes at startup is healthy, and one throwing away thousands
is telling you the baud rate is wrong, which no amount of reading the payloads
will say.

**Test the splits.** A test that feeds a whole frame proves almost nothing. Feed
the same frame cut at every position, including between the start byte and the
length, and feed two frames in one chunk. Those are the cases the robot will
produce and the desk will not.
