## The lesson contract

Every lesson directory holds exactly this, and `rcpp audit` enforces it with
rules L001 to L028:

```
lesson.json        id, title, minutes, platforms, requires, artifact, breaks_first
CMakeLists.txt     one line: rc_add_lesson()
reference/solution.hpp   the worked implementation, which must always pass
exercise/solution.hpp    the learner's copy, which must always fail
tests/test_*.cpp   one suite that grades both, chosen by include directory
checks/*.cpp       optional, code that must not compile
quiz.json          six questions, stages pre, check, post
docs/en.md         the lesson
```

Rules worth knowing without reading the source:

- **L016** no em dashes anywhere.
- **L019** a lesson claiming a toolchain must build on it. A skipped Qt lesson
  is a local convenience and a hard error under `RC_STRICT_CLAIMS` in CI,
  because a skip that reports success is the worst outcome a gate can produce.
- **L021** a lesson may not use vocabulary no lesson in its prerequisite chain
  teaches. It tracks 14 facilities and skips `tests/`, since tests are author
  code rather than learner code. It caught 01-10 using fixed width integers
  that only 08-01 claimed, and 08-01 sorts later. Lambdas were added to it
  after 02-08, which found that 03-04 and 11-01 had been using them since
  before anything taught them.
- **L022** no local `constexpr` used inside a lambda. MSVC C3493. Tripped three
  times.
- **L026** a Qt lesson carries a `fallback` naming the terminal lesson that
  covers the same ground without Qt.
- **L028** the `**Platforms:**` line in a lesson page names the toolchains
  `lesson.json` claims. Added after finding that no page mentioned the clang
  lane and one still said it was not claimed on Windows.
- **L027** a lesson may not require one that sorts after it. A curriculum with a
  stated order must not send a learner forward.

## Discipline

These are the rules the lessons are written to, and they are the reason the
numbers in the docs can be trusted.

**Measure, do not assert.** Every table in every lesson doc is printed by that
lesson's own suite, or was produced by a named experiment whose method is
stated. No lesson quotes a number it did not produce.

**Prove the trap bites.** A lesson about a mistake demonstrates the mistake
failing. Where the failure is a compile error it lives in `checks/`, because a
test can only assert what runs.

**Never gate on an absolute time.** Benchmarks are best of N, interleaved, and
compared against each other rather than against a constant. The machine drifts:
measured in 05-05, medians moved from 41.21 to 48.79 microseconds across a
single run with the fastest sample rising from 38.38 to 47.47, which is state
change and not noise.

**Deterministic noise.** An LCG plus Irwin-Hall rather than
`std::normal_distribution`, so published tables are byte identical across
standard libraries.

**The exercise must fail cleanly.** Exit non zero with a readable report, never
a crash. `tools/ci/exercises-fail-cleanly.sh` enforces it and needs a Debug
tree, because the assertions it looks for are compiled out of a release build.

**Every artifact graduates.** A lesson that ships an artifact moves a named
header into a librc module, and every librc header must compile alone and
twice.

## This machine

Facts that were expensive to establish.

**GCC 11's thread sanitizer reports false races on a timed condition variable wait.**
`wait_until` with a `steady_clock` deadline, and `wait_for`, call
`pthread_cond_clockwait`, which libtsan from GCC 11 does not intercept. It never
sees the mutex released during the wait and reports `double lock of a mutex` and
data races in correct code: 11 warnings on 07-06's suite. Measured on a twelve
line program, 2 warnings on gcc 11 and 0 on clang 14, and none for `wait()` or a
`system_clock` deadline. Use clang's: `cmake -DCMAKE_CXX_COMPILER=clang++-14
-DRC_SANITIZE_THREAD=ON`, which reported nothing on three runs. Do not "fix" the
program with `system_clock`, which makes a timeout jump when the clock is
adjusted. The `tsan` preset uses the default compiler, so it has this problem.
`E-TSAN-0002`.

**Neither gcc 11's nor clang 14's thread sanitizer sees `timed_mutex::try_lock_for`.**
It is `try_lock_until` on a `steady_clock` deadline, which calls
`pthread_mutex_clocklock`, and neither runtime intercepts it, so a lock taken that
way is invisible and the matching `unlock` is reported as `unlock of an unlocked
mutex`. 15 of 15 runs on a twelve line program under each; 0 of 15 for a
`system_clock` deadline. It fires only when the timed acquisition succeeds, so it is
intermittent: 7 of 25 runs on 07-09's first draft. Clang 14 does intercept
`pthread_cond_clockwait`, so it is clean for `E-TSAN-0002` and not for this. Poll a
plain `try_lock` against a `steady_clock` deadline in tests (0 of 30 under each), and
do not move production timeouts to `system_clock`. `E-TSAN-0003`.

**sudo needs a password and there is no tty.** There is an X11 session on
`DISPLAY=:1` and `zenity` is installed, and it is the only askpass helper
present. Write a helper that runs `zenity --password`, then
`DISPLAY=:1 SUDO_ASKPASS=<helper> sudo -A <command>` with the sandbox disabled.
A dialog appears on the desktop and the password reaches sudo without passing
through any transcript or log. Run `sudo -k` afterwards.

**Qt is 6.2.4 from apt.** So `QQmlApplicationEngine::objectCreationFailed` does
not exist, it arrived in 6.4; detect a failed load with `objectCreated` and a
null object, or an empty `rootObjects()`. The Windows lane runs 6.5.3, so the
baseline is the oldest claimed lane.

**Qt Quick needs a runtime as well as a toolkit.** `qt6-declarative-dev`
compiles and links a `QQmlApplicationEngine` program and cannot run one. The
modules are separate packages, and `qtqml-workerscript` and `qtquick-templates`
are not guessable. Full list in [PLATFORMS.md](PLATFORMS.md).

**Ubuntu 22.04 ships no standalone Qt 6 `qml` binary.** `/usr/bin/qml` is a
qtchooser stub answering `could not find a Qt installation of ''`, which reads
like a broken install and is not one. The curriculum never uses it.

**ROS 2 Humble is already installed.** `ros-humble-desktop`, the `ros2` CLI
works, 411 packages available. Phase 17 is not blocked.

## Measurements that changed the design

Kept because each one was arrived at by being wrong first, and the wrong
version is the intuitive one.

- **Rewind and replay is worse than forward projection** once latency exceeds
  the fix interval, because it discards intervening corrections. 16-03.
- **An innovation monitor sees nothing at constant speed**, 0.921 against
  0.935. Only stop and go exposes it. 16-05.
- **Pure pursuit has no U curve with a perfect pose.** The U appears only
  because the estimate is imperfect. 16-04.
- **A blank wall gives Otsu threshold 0 and one blob of 200 by 200.** The
  failure is finding everything, not nothing. 15-06.
- **A reference built from more integration steps gets worse past 10k steps.**
  06-06.
- **Padding and index caching in an SPSC queue are worth nothing alone and
  about 80 percent together.** 07-05.
- **Coverage is a floor, not a score, and a suite that asserts nothing proves
  it.** A program calling five functions and asserting nothing reported 100
  percent of 5 lines with 0 never run, while a deliberate `>` for `>=`
  survived. On `return a && b`: lines 100 percent, branches executed 100
  percent, taken at least once 50 percent. 05-07.
- **Counting a gcov file by hand took three attempts**, and two of the wrong
  answers flattered the result. `#####` alone gave 5 never-run lines where the
  answer was 7; adding `=====` fixed that and still disagreed on the total
  because the `digits*` form was not counted as code. The third attempt agreed
  with gcov exactly, and the parser now matches it on four real files. 05-07.
- **01-13's own suite covers 89.06 percent of its artifact**, with 7 lines
  never run, among them the `--name=value` branch of a private lookup and its
  not-found return: reachable, unexercised, because every call in the suite
  used the other spelling. The useful output of a coverage run is the list,
  not the percentage. 05-07.
- **My own sanitizer lane was never instrumented, for a whole session.** The
  option is `RC_SANITIZE_ADDRESS` and I was passing `RC_SANITIZE`, which CMake
  accepts in silence as a variable nothing reads. Continuous integration used
  the correct option throughout, so coverage was always real and only my local
  claim was false. The tell was a measurement that refused to move: 02-09's
  heap test reported the same 16 of 32 in both lanes, where genuine
  instrumentation gives 0 of 32. Ask the build graph, not the command line.
  04-07.
- **The two sanitizers overlap and neither is a superset.** Address is blind
  to signed overflow; undefined reported a read past the end of a block when
  the size was known at compile time and nothing at all when it was not. Of
  five common defects the pair this curriculum builds with finds three, and
  the two it misses are the two measured most carefully elsewhere, which is
  not a coincidence. 04-07.
- **Undefined cost more than address here**, 4.1x against 1.8x on an
  arithmetic-heavy loop, the reverse of the usual assumption. One workload, so
  the useful conclusion is that both are cheap enough for every push and
  neither is cheap enough to ship. 04-07.
- **`#if defined(__has_feature) && __has_feature(x)` does not compile on
  gcc.** The && does not protect the right hand side: the preprocessor parses
  the whole expression first, and an unknown identifier followed by a
  parenthesis is a syntax error rather than zero. The tests have to be
  nested. 04-07.
- **The address sanitizer moves locals off the stack entirely.** With
  detect_stack_use_after_return, which the sanitizer lane has on by default,
  locals go to a heap allocated fake stack so a pointer outliving its call can
  be caught. Measured: 4 of 4 steps downwards and a 64 byte frame without it,
  0 of 4 and an apparent -896 with it. 02-10's first draft asserted the
  growth direction unconditionally, passed locally and failed in CI, which is
  the mistake 04-07's own header warns about. The suite now asserts the
  layout only where the layout is real. 02-10.
- **A recursion with 64 byte frames died at depth 130860**, signal 11, status
  139, with no message and no last line of output. 8 MiB over 130860 is 64
  bytes a frame, so the depth you can afford is the limit divided by the
  frame. The Windows default stack of 1 MiB gives an eighth of the room.
  02-10.
- **A large local costs its space on paths that never run it.** A 15625 KiB
  array declared in main crashed a branch that only used a vector and never
  touched the array; moving the array into its own function made that branch
  survive. The frame is allocated on entry, not at the declaration. 02-10.
- **Both compilers accept a variable length array in silence** under
  -Wall -Wextra. It is a C99 extension, not C++, and -Wvla or
  -pedantic-errors rejects it on both. Not a checks/ case for that reason.
  02-10.
- **Ninety eight warnings came from one defect.** A warning is reported per
  translation unit, so a defect in a header is counted once per includer.
  Measured: one bad comparison, three translation units, 3 warning lines at 1
  distinct site. Count sites to size the work, lines to size the noise. The
  same source is not even comparable between compilers: gcc gave 4 lines at 3
  sites where clang gave 3 at 3. 04-08.
- **The exercise gate had a path that reported nothing and failed nothing.** A
  target that built but whose executable could not be found hit a bare
  `continue`, so the gate could exit 0 for work it had not done. Found by
  counting its output, 105 lines for 106 lessons, not by reading it. It now
  reports and fails, and checks that every listed target produced a line.
- **A crash loses buffered output, and the line you never saw is not the line
  it stopped at.** Four lines printed before a deliberate segmentation fault,
  into a pipe: the printf and the cout arrived, the cerr arrived, and the cout
  after it was lost. The first two survived only because writing to std::cerr
  flushed them, since cerr is tied to cout. With no cerr at all both buffered
  lines were lost and the output stopped two statements early. 00-09.
- **The stdout and stderr reordering everyone warns about does not apply to
  iostreams.** With printf and fprintf(stderr) into a pipe, stderr arrived
  first and stdout afterwards in a block. With std::cout and std::cerr the
  order was kept, because of that tie. Rule L018 forbids printf, and this is
  the measured reason rather than a style preference. 00-09.
- **An exit status of 256 reports success.** Only the low eight bits of main's
  return value survive, measured: 256 arrived as 0, 257 as 1, -1 as 255. So
  `return failures;` is wrong at exactly 256 failures, and a status above 128
  means the program probably did not choose to stop, 139 being 128 plus
  SIGSEGV. 00-09.
- **The benchmark measured nothing at -O2 and the test failed.** A guard of
  `if (total < 0) std::cout << "";` reads like it keeps the work and does not,
  so the optimiser deleted both loops and each reported 0.0 us. A volatile
  store fixed it. With the work restored the table beat the loop 6.9x at -O0
  and 20.7x at -O2 on gcc, 8.7x and 7.6x on clang, so the direction is
  asserted and the ratio is not. 03-11.
- **An agreement test passed with both sides stubbed to return 0.** Checking
  that two implementations agree says nothing when both are equally broken:
  agreement is evidence that neither is uniquely wrong, not that either is
  right. Anchor to known answers first, then compare. 03-11.
- **Undefined behaviour is not a constant expression**, which makes compile
  time evaluation a correctness tool before a speed one. The unwritten read
  that no compiler warned about and no sanitizer caught in 02-09 is a hard
  compile error on both compilers inside a constant expression. 03-11.
- **L022 caught a constexpr inside a function for the fifth time in this
  repository**, four of them after the atlas entry for it was written. That is
  the argument for a rule in the tool over a note in a document. 03-11.
- **`atoi` got three of five user-typed strings wrong, in three different
  ways**: 0 for two things that are not numbers, indistinguishable from a
  deliberate 0, and 3 for "3.9", a real number read as a different one. On a
  20 digit number it is undefined rather than wrong, and returned -1, turning
  a mistyped speed limit into a negative speed. 01-13.
- **A missing command line argument is not an out of bounds read.** The
  standard guarantees `argv[argc]` is null, so reading `argv[1]` with no
  arguments is valid and yields a null that looks like a value. Worse than a
  wild pointer, which crashes where the mistake is. 01-13.
- **A lookup with a fallback destroys information at the return statement.**
  Absent, misspelled, and given-with-no-value all come back as the default,
  and only the first of those should. This repository's own
  `tools/rcpp/main.cpp` has that shape, which is where the lesson came from.
  01-13.
- **A sliced copy is not broken, it is smaller.** The same object read 21.5
  through a `const LooseSensor&` and 0 by value, because `sizeof(LooseSensor)`
  is 8 and `sizeof(LooseThermometer)` is 16, so dispatch correctly picked the
  base implementation on a copy that really was a base. Silent on gcc, on
  clang, and on clang under `-Weverything`. 03-10.
- **One virtual function costs one pointer per object**, 16 bytes to 24 for
  identical data, which is why no value type in librc has one and the three
  interfaces that do are the only ones. 03-10.
- **The virtual destructor trap cannot be tested, only required.** Deleting
  through a non virtual base destructor leaked 2 allocations against 0,
  measured standalone, because the suite cannot run it: it is undefined
  behaviour and the sanitizer lane stops with new-delete-type-mismatch. gcc
  and clang warn only when the base already has another virtual function, and
  are silent for the handle-shaped bases this actually bites. The answer is a
  `static_assert` per interface. 03-10.
- **The same unwritten `int` read 1405118043 at -O0 and 0 at -O2.** Not a
  compiler bug: the read is undefined, so there was no correct answer to give,
  which is the whole mechanism behind works-in-debug-fails-in-release. 02-09.
- **A fresh heap block looked zeroed only because nothing had run yet.** A
  program whose first act is the allocation sees 32 of 32 bytes zero; the same
  code inside a suite that has already allocated sees 27. Of a freed and
  reclaimed 32 byte block, 16 bytes came back verbatim and 16 held the
  allocator's own bookkeeping. 02-09.
- **Neither the compilers nor the sanitizer lane catch the case that matters.**
  A struct member read inside a function it was passed to is silent on gcc and
  clang at both optimisation levels, and `-fsanitize=address,undefined` runs it
  clean and prints the garbage. The memory sanitizer is clang only, cannot be
  combined with the address sanitizer, needs an instrumented standard library,
  and here caught a trivial local while missing the struct member. The gap is
  why `rc/core/init.hpp` exists. 02-09.
- **The compiler warns about the safe construct, not the dangerous one.**
  `Pose p = {1.5};` is completely defined and warns on both gcc and clang as
  `-Wmissing-field-initializers`; give the members default initialisers and the
  identical brace is silent. `Pose p;` followed by a read across a call
  boundary warns on neither. 02-09.
- **An order dependence detector contaminated itself.** Written without a
  reset between its two passes, `run_in_both_orders` ran its backwards pass on
  what the forwards pass left behind, and a known leaky pair scored 1 forwards
  and 0 backwards instead of 1 and 2. The counts still differed, so
  `order_dependent()` was still true and the test asserting it still passed,
  reporting numbers that were not true. A tool for finding shared state cannot
  be free of shared state by accident. The reset is now a parameter, because
  the detector cannot know what the probes share. 05-06.
- **A lambda body of only `sizeof(payload)` does not require the capture**,
  which is what clang says as `-Wunused-lambda-capture`. Both compilers kept it
  and the allocation table was identical either way, but a measurement of what
  a capture costs must not rest on a capture the compiler may drop, so the body
  now reads a byte of it. 02-08.
- **Clamping a refused IK branch missed by up to 0.73 m on a 0.9 m arm**, and
  three of four such targets were reachable by the other elbow all along. The
  lesson became about branch selection rather than clamping. 13-05.
- **Returning a container by value copies nothing.** The buffer travels out, at
  `-O0` as well as `-O2`, so the out parameter written to avoid that copy
  avoids nothing. 01-11.
- **A `const int` sentinel silences clang's sign compare warning** where gcc
  still objects, so adding `const` to a variable removed a diagnostic. 01-07.
- **At `-O2` both gcc and clang delete the exit test** of a loop doubling a
  signed int, because overflow is assumed not to occur. 31 iterations at `-O0`,
  unbounded at `-O2`. 01-09.
- **An absolute tolerance of 1e-9 spans 4.5 million doubles at magnitude 1 and
  fewer than one at 1e9**, where no two distinct doubles can satisfy it. 01-08.
- **Erasing from a vector leaves every pointer valid and pointing at a
  different element.** Nothing is freed, so no sanitiser reports it, which makes
  it worse than the dangling case that crashes. 02-07.
- **assert does not evaluate its condition at all under NDEBUG.** A counter
  incremented inside one read 1 before and still read 1 after, in the same
  translation unit, so a check with a side effect silently loses it and a check
  without one silently stops checking. Every release configuration defines
  NDEBUG without saying so. 04-06.
- **One defaulted destructor cost 127 extra allocations.** Declaring
  `~X() = default;` on a struct holding a vector suppresses the implicit move
  constructor, so growing a container of 64 of them took 198 allocations
  instead of 71 on libstdc++, and 254 extra on the Microsoft debug library
  whose baseline is higher. `std::is_move_constructible` reports yes either
  way, because copying satisfies it; the nothrow variant is the one the
  library branches on. 03-09.
- **A loop's named sections came to 880 of 1000 microseconds.** The missing
  twelve percent was code nobody had thought to name, which is the usual place
  for a surprise, and a nested section makes the remainder go negative rather
  than the shares exceeding a hundred percent silently. 04-05.
- **Checking every field of a log line catches one bad line in three.** A row
  cut short parses as a valid shorter row, and a decimal comma in a comma
  separated file splits into an extra column of perfectly good numbers. Only
  counting columns catches either. 01-12.
- **An iterator over a ring's storage gives a correct sum and the wrong
  order.** A ring of four holding 3 4 5 6 keeps them in slots as 5 6 3 4, so
  every order independent check passes and only position dependent ones fail,
  and only after a wrap. 03-08.
- **Returning a lambda that captured a local by reference is accepted by both
  compilers**, while returning a reference to a local directly is refused by
  both. The same reference, hidden in a capture list, loses its diagnostic.
  02-08.
- **A static_assert does not shorten a template error on clang.** Constraining
  a template took gcc from 113 lines to 5 and took clang from 224 up to 254,
  because clang reports the assertion and instantiates the rest anyway. What it
  reliably fixes on both is the first error line, which is the one that gets
  read. 03-07.

## Known warnings

The Debug configurations that CI builds are warning clean. An optimised build
is not, and both remaining warnings were investigated and are false positives
in gcc rather than defects here. Recorded so the next person does not repeat
the investigation.

**51 of `-Wmismatched-new-delete`**, from `rc/test/leak_check.hpp`, in the six
lessons that both include it and use raw `new[]` and `delete[]`. gcc traces a
`delete[]` into the replaced `operator delete[]`, sees `std::free`, and pairs
it with the `new[]` at the call site without modelling that `operator new[]`
was replaced too and allocates with `std::malloc`. The pairing in the learner
code is correct.

It cannot be suppressed with `#pragma GCC diagnostic`, which was tried: the
diagnostic is emitted in a late pass after inlining, where lexical pragmas no
longer apply. A global `-Wno-` flag would hide it for learner code as well,
which is the wrong trade in the phase 02 lessons that teach the pairing. A
genuine mismatch is caught at runtime by the address sanitizer as
`alloc-dealloc-mismatch`, verified, and the sanitizer lane runs on every push.

**1 of `-Wstringop-overread`**, inside `<bits/stl_algobase.h>` on gcc 11,
reached through `std::vector::insert` inlined into a test in 08-04. A known
libstdc++ issue on that version rather than anything in this repository.

## Next, in the order it should be done

**Done.** `tools/rcpp` now reads its command line with
`rc::core::Arguments`, which makes the tool the first consumer of `librc`.
`has_flag` and `flag_value` are gone, replaced by `args.has()` and two
helpers, `read_option` and `read_count`, that report the case the old pair
could not: the user asked and left the value off.

Three live defects were measured before the change and again after.

| | before | after |
|---|---|---|

| `rcpp next --count abc` | 1 lesson, silently | exit 2, `--count needs a whole number` |
| `rcpp next --count 0` or `2.9` | 1 and 3 lessons | exit 2, `must be a whole number of at least 1` |

The third was not in the plan and was found while reading the two loops that

The misspelling case is now caught too, by the other half of what
`E-CPP-0056` prescribes: every command declares the options it knows and
refuses anything else, with a suggestion from an edit distance in
`tools/rcpp/util.cpp`.

```
$ rcpp list --phse 01
rcpp list: unknown option --phse
  did you mean --phase?
```

`rcpp next --cont`, `rcpp audit --jsn` and `rcpp verify --refrence` all answer
the same way. A bare `--` stops the checking, and `-h` and `--help` are always
allowed. A value that itself began with a dash would be mistaken for an
option, which no option in this tool takes.

**The scan, and what it has not yet been followed up on.** Scan each lesson's
`reference/` and `exercise/` code in curriculum order for C++ constructs, find
the first lesson that uses each, then find the first lesson whose page
discusses it. A large gap is a hole. It is crude, because it reads headings and
prose and a construct can be explained under a title that does not name it, so
every candidate below needs the check that sank three earlier premises: read
the pages before building anything. Candidates, by how many lessons use them:
`inline` (78 lessons, first discussed at 04-04), `size_t` (50, first at 01-07),
and `auto` (9, from 03-03, never discussed). `explicit`, checked next, turned out to be one symptom of a
larger hole, below.

Function-local `static` was the last on the list, and it was a better lesson than
the scan implied because the word means three things. At 02-03 a learner meets
`static int next_id = 1; const int id = next_id++;` with nothing said, and the
explanation is a clause at 05-01 and a case of the file-scope meaning at 04-04.
It is done as **02-12**: a static local outlives the call and is built on first
use, a static member belongs to the class and takes no space in the object, and a
counter of live objects has to count copies. Measured: a Wheel with a static
count was 8 bytes against 16 with the count in each object, a static data member
declared and never defined fails to link, and a counter that only the ordinary
constructor increments drifts down by one per copy.

The last lesson, **01-18**, was the one the scan could not find because it is not a
construct: nothing taught reading code someone else wrote. It gives five functions
with comments, 25 cases, and a table of guesses to fill in before running. Measured,
a reader who trusted every comment predicted wrongly in 12 of the 25, and the
control function, whose comment was exactly right, in none. It completes phase 01
and is the first phase finished to plan. The change it asks for is dividing by 1023
and nothing else, which moves 49 of 1024 answers; rounding as well moves 560, and
my own first draft did that and called it the least change until the lesson's own
output said otherwise.

`namespace` was checked next and confirmed. `std::` is in code from 00-03 and
`rc::core` is in the Ship It line of six lessons, rule L018 bans
`using namespace std;` in every lesson, and no page says what the two colons are or
why the ban exists. It is done as **01-17**, with the measurement that makes the
ban concrete and not stylistic: with `using namespace std;` in scope, a call
`clamp(5, 0, 3)` stopped reaching the global `clamp` that lesson 01-02 teaches and
ran `std::clamp` instead, returning an int where it had returned a double, with no
warning on gcc 11 or clang 14. 00-03 now has a sentence pointing at it where
`std::sqrt` first appears.

`explicit` led somewhere better. Reading the pages showed that "constructor" is
used from 01-13 and 02-03 onward and is **defined nowhere**: 03-01, "Classes",
teaches `class`, private data, `const` methods and invariants and does not
contain the word, writing only `RunningStatistics() = default;`. So the member
initialiser list, `explicit`, default member initialisers, and the rule that
declaring a constructor withdraws the default one were all met in code and
explained in no page. It is done as **02-11**, in phase 02 because 02-03 cannot
be understood without it, and the page says so. The lesson found by following one
construct's symptom to its cause is a better lesson than the one the scan named.

`inline`, the largest by count, was checked by reading 00-01, 00-02 and 04-04 and
turned out to be a contradiction and not a missing lesson. 00-02 teaches that a
function body belongs in one `.cpp` file, while every file a learner edits from
00-01 on is a header full of bodies marked `inline`. 04-04 explains the exception
in full, many lessons later. The fix was a sentence in 00-01 and a subsection in
00-02 saying what the word is for, why the lessons are header only, and that
this is a choice about the curriculum and not a rule about C++, with 04-04
named as the place the cost is measured. No new lesson was warranted.

The conditional operator `?:` was the smallest of them, used in 34 lessons and
never explained, and did not warrant a lesson. It is a subsection of 01-02's
"Deciding", with a test in that suite tied to the learner's `clamp`: it picks one
side, binds more loosely than `<<` so `out << "ok: " << flag ? ...` leaves
`ok: 1` in the stream (gcc 11 warns, clang 14 does not), and gives both sides one
type. A gap this size is a paragraph and a test, not a lesson.

Range-for was checked first by reading 01-02 and 01-04, which confirmed it: 01-02
teaches only the three part loop, and 01-04's own code is written with a range
loop that nothing explains. It is done as **01-16**. `auto` is now partly
covered there, since the lesson measures that `auto x` copies exactly as a named
type does.

01-14 found a hole in its own first draft, worth recording. The first test
asserted that a save which could not proceed refused and left the old file
untouched, and a stub that refused everything satisfied it, so the exercise
scored 1 of 8 before anyone had written a line. The test now also requires the
same setup, unblocked, to succeed. A refusal proves nothing from a function
that cannot also say yes.
