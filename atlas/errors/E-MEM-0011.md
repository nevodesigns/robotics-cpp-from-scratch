id: E-MEM-0011
title: A pointer into a vector that grew
match: one insertion is enough, when there is no room left
platforms: linux, windows
teaches: 02-07-the-pointer-that-was-right-yesterday
---

## Symptom

A pointer, reference, iterator or span into a `std::vector` reads rubbish, or
the program crashes somewhere unrelated. Under the address sanitizer it is a
heap use after free, in a buffer nobody called `delete` on.

It worked for months. It started failing when a sample buffer got longer, or
when a loop that collects readings ran one iteration more than it used to.

```cpp
const double* newest = &samples.back();
samples.push_back(reading);        // the buffer may move here
use(*newest);                      // and this reads freed memory
```

## Cause

A vector keeps its elements in one buffer. When it has no room left it
allocates a bigger one, copies everything across, and frees the old one.
Everything that referred to the old buffer now refers to memory that has been
handed back.

Measured with three readings and no slack:

| | capacity | buffer |
|---|---|---|
| before | 3 | where it was |
| after one `push_back` | 6 | somewhere else |

The reason this survives testing is that it does not happen every time.
Measured over twenty insertions into an empty vector: **six reallocations**,
with capacities 1, 2, 4, 8, 16, 32. Nineteen of those twenty insertions left
every borrowed pointer perfectly valid.

The growth factor is a standard library choice and not a rule, so do not build
anything on knowing it.

## Fix

**Ask before inserting.** `rc::core::would_reallocate(samples, 1)` answers
whether the next insertion will move the buffer, and it has to be asked
beforehand because afterwards every pointer that could have told you is stale.
Checked against what actually happened on a thousand insertions, no prediction
wrong.

**Reserve, and then borrow freely.**

```cpp
rc::core::reserve_for(samples, expected_count);
```

Measured: twenty insertions after reserving for twenty moved the buffer zero
times. This is the right answer for a sample buffer whose length you know, and
it is also what keeps allocation out of a control loop.

**Borrow an index, not an address.** An index survives reallocation. It does
not survive an `erase`, which is `E-MEM-0012`.

**Do not hold a span across an insertion.** A span is a pointer and a length
and both go stale. Take it, use it, drop it, inside one operation.

**Use `std::deque` or `std::list` when you genuinely need stable element
addresses.** Measured over 100 insertions, neither moved its first element.
They pay for it with a pointer chase per element, which phase 07 measures.
