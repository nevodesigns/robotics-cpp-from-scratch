id: E-IO-0013
title: A port configuration that reported success without applying
match: a pseudo terminal opens and configures like the serial port
match: expected .*SerialError::Ok
platforms: linux
teaches: 08-05-opening-a-real-port
---

## Symptom

Every frame fails its checksum, from the first one, on a link that is otherwise
delivering bytes steadily. The count of bytes read is healthy. The count of
valid frames is zero.

Nothing returned an error. `open` succeeded, `tcsetattr` returned zero, and the
port is in a state nobody asked for.

## Cause

POSIX says `tcsetattr` returns success if it managed to apply **any** of the
settings it was given. It is not an all or nothing call, and there is no way to
ask which parts it took.

So a baud rate the hardware cannot produce is not an error. It is a different
baud rate, applied silently, and a link running at the wrong rate delivers a
steady stream of bytes that are not the bytes that were sent. That is exactly
the signature above: plenty of data, no valid frames.

The same silence covers a `cfmakeraw` that was never called, or was called on a
different `termios` struct than the one passed to `tcsetattr`, which is easy to
do when the configuration grows past a screen.

## Fix

Read the settings back and check the ones that matter:

```cpp
termios applied{};
if (::tcgetattr(fd, &applied) != 0 ||
    ::cfgetispeed(&applied) != speed ||
    (applied.c_lflag & ICANON) != 0 ||
    (applied.c_iflag & IXON) != 0) {
  ::close(fd);
  return SerialError::ConfigureFailed;
}
```

Four lines, and they convert a mystery into an error code at the moment of
opening.

The value of that is worth stating precisely, because it is easy to read as
defensive noise. Measured on this lesson's own tests, with the check in place,
forgetting `cfmakeraw` makes `open` return `ConfigureFailed` and the failure is
reported where the mistake is. With the check removed, the same omission lets
`open` succeed and destroys data later, in a pattern that depends on the byte
values each message happens to contain. Same bug, and the check is the whole
difference between finding it in the first minute and finding it in the field.

Check the settings you depend on rather than all of them. Comparing the whole
struct fails on fields the driver is entitled to adjust, and a check that cries
wolf gets deleted.
