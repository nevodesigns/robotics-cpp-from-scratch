id: E-MEM-0016
title: A function that filled only part of its output
match: returned true and filled some of it
platforms: linux, windows
teaches: 02-09-the-value-that-was-never-written
---

## Symptom

A function takes a pointer to a struct, fills it in, and returns whether it
worked. It returns true. One field of the struct is wrong.

The call site is correct. The error check is there and it passed. The field
that is wrong is wrong in a way that looks plausible, so the bug is found
somewhere downstream, usually by the behaviour of the machine rather than by a
test.

```cpp
Pose p;
if (read_pose(&p)) {
  drive_towards(p);        // p.heading was never written
}
```

## Cause

This is the C shape that every device driver, every vendor SDK and every
operating system API uses, and it has a hole in it: the return value describes
whether the call succeeded, and nothing describes whether the output was
completely written.

A function that writes two of three members and returns true is reporting
honestly by its own lights. It did not fail. It simply did not finish, and
there is no channel for that.

The reason it survives review is that the missing field reads as whatever was
in the caller's stack frame, and during testing that is frequently zero or
something near zero, which for a heading, an offset or a velocity is a
perfectly ordinary value.

Nothing warns. Measured with gcc 11 and clang 14, a struct member left unwritten
and then read inside a function it was passed to produces no diagnostic on
either compiler at any optimisation level (`E-MEM-0014` has the full table),
and the address sanitizer does not look for it.

## Fix

Poison the output before the call, and count what came back unwritten.

```cpp
#include <rc/core/init.hpp>

Pose p;
rc::core::poison_bytes(&p, sizeof(p));
const bool ok = read_pose(&p);
RC_CHECK(ok);
RC_CHECK(rc::core::all_bytes_written(&p, sizeof(p)));
```

Measured in lesson 02-09 on a 24 byte `Pose` of three doubles:

| filler | bytes left unwritten |
| --- | --- |
| writes all three members | **0** |
| writes two and returns true | **8** |

Eight is `sizeof(double)`, and it names the field: the one the return value
said nothing about. The test that only checked the return value passed for
both.

This belongs in the test, not in the shipping code path. The point is to prove
once that the function fills what it claims to, so the call sites can go on
trusting the return value.

Two honest limits.

**It cannot tell your pattern from real data.** A byte the function wrote to
`0xff` on purpose is indistinguishable from one it never touched. Measured on
an eight byte frame where every byte was written and two of them happened to be
`0xff`, the counter reported two unwritten. For a struct of doubles the answer
is exact, because the pattern repeated is a NaN and no correct code writes that.
For raw bytes, read the count as a lower bound on what was written.

**Padding counts as unwritten**, because it is. A struct whose members are all
written but whose padding is not will report those bytes, which is correct and
occasionally surprising. `E-IO-0002` is the same fact from the other side,
where the padding in a struct sent whole is what arrives as nonsense.

The deeper fix, where the function is yours to change, is to return the value
instead of filling a pointer. A `Pose` returned by value cannot be partly
written, and lesson 03-02's error type carries the failure case without needing
a second channel.
