id: E-CPP-0046
title: An iterator over the storage instead of over the index
match: the iterator walks in logical order, not in storage order
platforms: linux, windows
teaches: 03-08-making-it-iterable
---

## Symptom

A moving window produces the right sum and the wrong everything else. The mean
is correct, the maximum is correct, and the oldest reading, the newest reading,
the trend and the plot are all wrong. A pose trail draws the right points with
one jump in it.

It is right until the buffer fills for the first time, and wrong afterwards.

```cpp
const T* begin() const { return storage_; }          // the raw array
const T* end() const { return storage_ + count_; }
```

## Cause

A ring buffer's elements are not in array order. The oldest one is wherever the
reuse happened to leave it, and `operator[]` exists to do that arithmetic.

Measured on a ring of four with 1 to 6 pushed into it:

| | order |
|---|---|
| `operator[]` | 3 4 5 6 |
| an iterator over `operator[]` | 3 4 5 6 |
| the raw slots | **5 6 3 4** |

The right four readings, in the wrong sequence.

Which is why the sum is right. `std::accumulate` does not care about order, so
every order independent check passes and the bug hides behind them. Anything
that asks about position fails: `front`, `back`, `max_element`'s iterator,
`adjacent_difference`, a plot, a derivative.

And it only appears after a wrap, so a test that pushes fewer readings than the
capacity cannot see it, which is the same blind spot as `E-CPP-0041`.

## Fix

**Build the iterator on `operator[]`, not on the storage.** The indexing
already does the wrap arithmetic, so an iterator that goes through it is
correct without doing the work twice.

```cpp
reference operator*() const { return (*container_)[index_]; }
```

That is also the whole reason `rc::core::IndexIterator` takes a container and
an index rather than a pointer.

**Test with an order dependent check, past the capacity.** Comparing the walked
sequence against the sequence from `operator[]` is one line and it is the only
check that distinguishes these two implementations. A sum does not.

**Never hand out a pointer into a ring buffer's storage at all.** It invites
pointer arithmetic from the caller, which has no way to know about the wrap.

**If you do want the raw slots for a memcpy, say so in the name.** A
`raw_storage()` that is documented as being in slot order, and used only for
writing a whole buffer out, is a different and legitimate thing from `begin()`.
