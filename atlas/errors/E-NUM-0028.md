## Symptom

A robot behaves for half an hour and then something with time in it goes wrong:
a timeout fires at once, a rate computes as negative, a filter blows up. Or a
position counter that was exact for a while stops being exact, off by one and
then by two.

## Cause

Two ways a number is put somewhere too small for it.

**A wide integer in a narrow one wraps.** A microsecond clock held in a 64 bit
integer is fine. Held in an `int` it reads 2147000000 at 2147 seconds and
**-2146967296 at 2148 seconds**, which is 35.8 minutes. At 3000 seconds it reads
-1294967296. The conversion down is defined by the implementation, not the
standard, so it wraps quietly into a believable negative number rather than
crashing.

**A float holds whole numbers exactly only up to 16777216**, which is two to the
24th. Measured: 16777217 stored in a float comes back as **16777216**, and
100000001 as 100000000. Of 100 integers starting at 16777216, **50** were lost.
A `double` holds every 32 bit integer: none of 65536 samples across the whole
range was lost.

An encoder count held as a float is exact for a while and then quietly stops
being so.

## Fix

Keep the wide type wide, and convert down only through a check.

```cpp
#include <rc/core/narrow.hpp>

const auto micros32 = rc::core::to_int(elapsed_micros);   // elapsed_micros is long long
if (!micros32.ok) { /* it does not fit: keep it wide */ }

rc::core::survives_float(count);      // false once a float would lose it
```

Use `double` for a count that has to stay exact, and `long long` for a clock.

Braces are the one place the language checks this for you:

```cpp
double d = 3.7;
int x{d};          // error: narrowing conversion of 'd' from 'double' to 'int'
int y = d;         // accepted, silently
int z = static_cast<int>(d);   // accepted, and says someone decided
```

Prefer braces, and when the loss is intended, a cast that says so.
