id: E-QT-0009
title: A widget repainted at the rate its data arrives
match: adding a sample never asks for a repaint
match: refreshing asks for exactly one repaint
platforms: linux, windows
teaches: 10-03-a-live-plotter
---

## Symptom

An application with a live chart stops responding. Buttons take a second to
react, the window does not move when dragged, and the chart itself updates in
jerks rather than smoothly.

A profiler shows almost all the time inside painting, which looks like the
drawing being too slow. It usually is not: the drawing is being asked for far
more often than anything can use.

## Cause

The widget asked for a repaint every time a sample arrived:

```cpp
void addSample(double time, double value) {
  series_.add(time, value);
  update();                       // the bug
}
```

A sensor at one kilohertz asks for a thousand repaints a second. A screen shows
sixty. Nine hundred and forty of those pictures are prepared and thrown away,
and the event loop is busy making them instead of handling the click that just
arrived.

`repaint()` is the worse version of the same mistake, because it paints
**synchronously** rather than asking the event loop to do it later, so nothing
is coalesced at all.

The general shape is worth naming, because it appears well beyond Qt: **the rate
data arrives at and the rate a person can perceive are different rates, and
tying them together lets the faster one set the pace for everything.**

## Fix

Separate them. Arriving data marks the picture out of date; something running at
the frame rate asks for the repaint.

```cpp
void addSample(double time, double value) {
  series_.add(time, value);
  stale_ = true;                  // and nothing else
}

void refresh() {                  // a QTimer at 30 or 60 Hz calls this
  if (!stale_) return;            // nothing changed, so nothing to draw
  stale_ = false;
  update();
}
```

Two properties, and the second is as important as the first.

**A thousand samples cost one repaint.** The data rate no longer reaches the
event loop at all.

**A frame with no new data costs nothing.** A timer fires whether or not
anything arrived, and a chart that repaints on every tick regardless burns a
core redrawing an identical picture. The stale flag is what turns the timer from
a schedule into a permission.

`update()` rather than `repaint()`, always, unless you can say precisely why
not. `update()` asks the event loop to paint when it next can and merges several
requests into one; `repaint()` paints immediately, which is what you want in
approximately no situations that arise in normal code.

If the data arrives on another thread, none of the above is enough on its own:
a widget may only be touched from the thread that owns it, and the crossing is
what signals and slots with a queued connection are for.
