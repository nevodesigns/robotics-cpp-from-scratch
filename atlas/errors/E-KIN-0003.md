id: E-KIN-0003
title: A numerical solver that never stops, or never says it stopped short
match: an unreachable target stops rather than looping for ever
match: giving up is reported, not disguised as an answer
platforms: linux, windows
teaches: 13-03-reaching-without-a-formula
---

## Symptom

Two failures that come from the same missing idea, and one is much worse than
the other.

**The program hangs.** A target outside the workspace is commanded and the
solver never returns. Nothing crashes, nothing logs, and the control loop it was
called from misses every deadline after that.

**The arm goes to the wrong place.** The solver returns angles that do not reach
the target, and they look exactly like angles that do, because there is nothing
in the result that says otherwise.

## Cause

An iterative solver improves a guess. Nothing in the arithmetic knows whether
the guess can be improved to the point of being correct.

For an unreachable target the error simply stops going down. There is no
exception, no special value and no signal: the loop is still doing its job, and
its job has no end.

```cpp
while (error > tolerance) { /* the bug is that this is a while */ }
```

The second failure is subtler and more common. A solver that caps its iterations
and returns the angles it had reached, without saying it ran out, has made a
non answer indistinguishable from an answer. The caller drives to it.

## Fix

Cap the iterations, and report what happened:

```cpp
struct ReachResult {
  std::vector<double> angles;
  int iterations = 0;
  double error = 0.0;
  bool converged = false;   // reported, never assumed
};
```

Every caller then has to look at `converged`, which is the point. The angles are
still there and are still the best it found, which is often useful: they are a
reasonable place to start from next time, or a reasonable thing to show on a
screen. What they are not is a command.

Three things worth returning rather than one boolean.

**The error it got to.** A solver that stopped at 1e-7 was nearly there and
probably needs more iterations. One that stopped at 0.4 was asked for something
impossible, and those want different responses.

**The iteration count.** Convergence taking ten times longer than usual is how a
singularity announces itself before it becomes a stall. Measured in lesson
13-03: 390 iterations at a comfortable target, 1281 nearer the edge, 5236 nearer
still, then no convergence at all.

**The angles**, always, even on failure.

One more thing about caps. Make the limit an option rather than a constant, and
choose it from the deadline the caller has rather than from what looked
sufficient while testing. A solver inside a control loop running at a kilohertz
has a millisecond, and a thousand iterations of anything is not going to fit.
