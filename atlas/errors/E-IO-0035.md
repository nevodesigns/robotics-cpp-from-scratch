## Symptom

An arm ends up further along than it was told, by a small and irregular amount that
grows with the number of commands and with the badness of the cable. A counter is
too high. A relay is toggled back. The log shows each command once.

## Cause

A retry is the same command sent again, and the requester cannot know whether the
first one was lost or only its answer was. If the answer was what was lost, the
device **did** what it was asked, and now does it a second time.

Matching ids on the requester's side fixes the wrong answers and leaves this
untouched. Measured:

| requester | position (should be 200) |
|---|---|
| matches the id | 227 |
| matches the id, device remembers | 200 |

The overshoot is exactly the number of resends, 27, because each of them was a
command the device had already carried out.

## Fix

The device's half of the promise. It keeps the last id it answered and what it said,
and when the same id arrives it replays the answer instead of repeating the act:

```cpp
if (cache.lookup(id, remembered)) {
  reply(remembered);          // seen this one, do not do it again
} else {
  execute();
  cache.remember(id, response);
}
```

A command that is safe to do twice, a request for a reading, a move to an absolute
position, needs none of this. One that is relative, or toggles, or counts, does.
The better design is to avoid the second kind where the protocol can: "move to 200"
repeated is harmless and "move by one" is not.
