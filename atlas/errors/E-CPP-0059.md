## Symptom

```
error: array bound is not an integer constant expression
error: the value of 'size' is not usable in a constant expression
error: non-type template argument is not a constant expression
```

A variable is `const`, which was supposed to mean constant, and the compiler
will not accept it where a constant is needed.

## Cause

`const` and `constexpr` answer two different questions, and the words make it
sound like one.

**`const` is about writing.** It says nobody may change this through this
name. It says nothing about when the value is known.

**`constexpr` is about knowing.** It says the value is computable during
translation, and a declaration that cannot deliver that is an error.

So a `const` initialised from something only the running program knows is a
perfectly good `const` and not a constant expression:

```cpp
const int size = readings.size();     // const, not a constant expression
int buffer[size];                     // refused, and this is not C
```

The confusing part is that `const` sometimes works, which is why the model
never gets corrected:

```cpp
const int kCount = 8;                 // initialised by a literal
int buffer[kCount];                   // accepted
```

A `const` integral initialised by a constant expression *is* usable as one,
by a rule inherited from C++98 that exists for exactly this case. That rule
covers integral types only, so the same thing with a `double` fails, and it
does not extend to anything a function computed. The result is a feature that
appears to work until the first time it matters.

Two more places the distinction shows up.

**`const` on a member function** is a third meaning again: this function does
not modify the object. Lesson 03-01 covers it, and it has nothing to do with
compile-time evaluation.

**`constexpr` on a variable implies `const`.** A `constexpr` variable cannot
be assigned to, so writing both is redundant.

## Fix

Say which you mean.

```cpp
constexpr int kCount = 8;                // known at build time, and checked
const int size = readings.size();        // known when it runs, not reassignable
```

Prefer `constexpr` for anything that really is a build-time constant: a size,
a limit, a conversion factor, a polynomial coefficient. It costs nothing, and
it makes the declaration fail if somebody later initialises it from something
runtime, which is the error you want rather than a silent demotion.

For a runtime size, the container is the answer and not a variable-length
array, which C++ does not have:

```cpp
std::vector<double> buffer(size);        // runtime size, and it frees itself
```

`rc/core/table.hpp` is the build-time case in full: the table variable is
`constexpr`, so a build that could not fill it in during compilation is a
build that fails. `E-CPP-0058` is what happens when that keyword is left off.
