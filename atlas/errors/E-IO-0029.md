## Symptom

A position estimate drifts and always in the same direction, and by an amount that
depends on how busy the program was. A distance travelled is short. A step counter
undercounts. It gets worse under load and better on a quiet machine, which sends
the search towards the CPU rather than the policy.

## Cause

"Keep the newest" is a policy for **states**: a position, a temperature, a battery
voltage, a joint angle. Each message says what is true now, so a newer one replaces
an older one and nothing is lost by skipping.

It is wrong for **changes**: an encoder count delta, a gyro increment, a step. Each
message says how much happened since the last, so the sum is what matters and a
skipped message is a piece of the sum thrown away.

Measured, a thousand messages each saying +1, drained a hundred at a time:

| | total |
|---|---|
| a loop that integrates the newest of each drain | 10 |
| what the skipped messages carried | 990 |
| the truth | 1000 |

Nothing is unaccounted for. It was received and counted as skipped, and used for
nothing.

## Fix

Decide which kind of message it is before choosing the policy, and let the message
format help. A change message should carry a running total, which turns it into a
state: the newest total is then enough, and a lost message costs nothing. Where it
cannot, handle every message and make the loop fast enough or the work small
enough to keep up, and count the skipped ones so a policy change cannot go
unnoticed.
