id: E-QT-0017
title: A QObject deleted by a thread that does not own it
match: an object is destroyed by the thread it lives in
match: on its own thread it is deleted at once
platforms: linux, windows
teaches: 09-04-who-deletes-this
---

## Symptom

A crash inside Qt's event delivery or its connection lists, on shutdown or when
a worker is stopped. It appears on one machine and not another, or once a week,
or only in a release build. The stack has no frames of yours in it.

Or nothing crashes and a signal is delivered to an object that has been
destroyed.

## Cause

A `QObject` belongs to a thread: the one it was created in, or whichever it was
moved to. Its destructor takes it out of that thread's event queue and unhooks
its connections, and both of those are structures that thread owns.

Deleting it from another thread modifies them without synchronisation, which is
a race. Like most races it usually appears to work, because the window is a few
instructions wide and most of the time nothing else is touching the queue.

```cpp
worker->moveToThread(&thread);
thread.start();
// ...
delete worker;   // from the main thread. Wrong, and usually silent
```

## Fix

Delete it from whichever thread it belongs to, and let the code say which that
is.

```cpp
inline void delete_from_its_own_thread(QObject* object) {
  if (object == nullptr) return;
  if (object->thread() == QThread::currentThread()) {
    delete object;
    return;
  }
  object->deleteLater();
}
```

On its own thread the deletion is immediate and no event loop is involved. From
anywhere else, `deleteLater` posts the deletion to the thread that owns the
object, and **that thread's own loop performs it**. Measured, the object stays
alive until the worker's loop is given a chance to run, and is gone by the time
the thread has finished.

This is the one place `deleteLater` is not a convenience. It is the only correct
answer.

Three things that follow.

**Order the shutdown.** Ask the object to delete itself, then quit the thread,
then wait for it. Quitting first can leave the deletion posted to a loop that
will never run again, which is a leak rather than a crash and is harder to see.

**Give worker objects no parent across a thread boundary**, or the parent will
try to delete them from its own thread on the way out. A worker owned by its
thread, deleted through `deleteLater`, is the arrangement that survives.

**Check `thread()` rather than assuming.** `moveToThread` can be called from
anywhere and an object may not live where it was written, which is exactly what
lesson 09-03 measured about queued connections.
