# A Toolchain File That Cannot Lie: Generating It From the Triple, Checking It, and the Setting That Links the Host's Libraries Into the Robot

> A cross build that does not fail is not a cross build that worked. It may have built, quietly, for the machine it was sitting on.

**Type:** Build
**Time:** about 110 minutes
**Platforms:** Ubuntu 22.04 (GCC 11, Clang 14), Ubuntu 24.04, Windows
**Hardware:** none
**Prerequisites:** 20-01, 04-01, 03-03, 01-05

## The Problem

CMake builds for another machine when it is told to, in a **toolchain file**: which compilers, which system, where the target's headers and libraries are. It is a short file and it is written by hand once, copied from somewhere, and trusted for years. It has a handful of settings that **fail silently**: a build that uses the wrong library, the wrong compiler flag or the wrong tool still produces a binary, and the binary is the wrong one.

This lesson generates the file from the triple of lesson 20-01 so that it has one source of truth, checks a hand-edited one for the settings that matter, and shows what the three ways of finding a library do when the one you want is missing.

## The Concept

### Generated from the triple

`from_triple("aarch64-linux-gnu", "/opt/sysroots/rpi4")` fills in the rest: the system name `Linux`, the processor `aarch64`, the compilers `aarch64-linux-gnu-gcc` and `aarch64-linux-gnu-g++`. `render` writes it, in a fixed order, one setting to a line:

```
# generated by rc::deploy, do not edit
set(CMAKE_SYSTEM_NAME Linux)
set(CMAKE_SYSTEM_PROCESSOR aarch64)
set(CMAKE_C_COMPILER aarch64-linux-gnu-gcc)
set(CMAKE_CXX_COMPILER aarch64-linux-gnu-g++)
set(CMAKE_SYSROOT /opt/sysroots/rpi4)
set(CMAKE_FIND_ROOT_PATH /opt/sysroots/rpi4)
set(CMAKE_FIND_ROOT_PATH_MODE_PROGRAM NEVER)
set(CMAKE_FIND_ROOT_PATH_MODE_LIBRARY ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_INCLUDE ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_PACKAGE ONLY)
set(CMAKE_TRY_COMPILE_TARGET_TYPE STATIC_LIBRARY)
set(CMAKE_CXX_FLAGS_INIT "-mcpu=cortex-a72 -O2")
```

Thirteen lines. The same spec gave the same text every time, a spec with no sysroot or no flags left those lines out, `arm-linux-gnueabihf` got a processor of `arm`, and a flag containing quotes was escaped. The `FIND_ROOT_PATH_MODE` lines carry the whole idea: **programs** are found on the host (a code generator that runs during the build must run on the machine doing the building), but **libraries, headers and packages** are found in the sysroot, **and only there**. A triple that cannot be read gives an empty spec and nothing is written. See `E-DEPLOY-0004`.

### What is wrong with one that was written by hand

`validate` takes a specification and names what is wrong, in a fixed order. A spec for `aarch64-linux-gnu` that had been copied and edited gave **6 problems**:

- `c_compiler empty`
- `system_name should be Linux` (it said Windows)
- `processor should be aarch64` (it said x86_64)
- `sysroot not an absolute path` (`sysroots/rpi4`)
- `cxx_flags -march=native is the machine doing the build`
- `cxx_flags -mtune=native is the machine doing the build`

The last two are the quiet ones. `-march=native` is the most copied flag in C++, and it means **the CPU of the machine that is compiling**: in a cross build that is the laptop, and the binary uses instructions the robot does not have. The compiler does not complain. It cannot know. A Windows sysroot with a backslash, `C:\sysroots\win`, gave one problem, `has a backslash` (CMake reads it as an escape). A sysroot that was not there gave `does not exist`, and an unreadable triple gave one problem on `triple` and nothing else was checked. See `E-DEPLOY-0005`.

### Which library did it find

`find_library` models the three modes of CMake's search. The sysroot has `libz` and `libm` built for `aarch64`. The host has its own `libz` and a `libusb` built for `x86_64`. The sysroot has no `libusb`.

| mode | libz | libusb |
|---|---|---|
| ONLY | aarch64 | **missing** |
| BOTH | aarch64 | **x86_64** |
| NEVER | **x86_64** | not looked for in the target |

With **BOTH**, the missing `libusb` is replaced, without a word, by the host's: a library for the wrong processor, which will fail to link at best, and at worst be found by a build that only checks the name. With **ONLY**, the same situation is an error at the moment it happens, "libusb not found", which is the right answer: it says the sysroot needs the library. **NEVER** finds the host's `libz` even though the target has one, which is right for a program and wrong for a library. The default in CMake is BOTH, and the toolchain file's job is to change it. See `E-DEPLOY-0006`.

## Use It

`rc/deploy/toolchain.hpp` joins `rc::deploy`.

```cpp
rc::deploy::ToolchainSpec spec = rc::deploy::from_triple("aarch64-linux-gnu", sysroot);
spec.cxx_flags = {"-mcpu=cortex-a72", "-O2"};
const auto problems = rc::deploy::validate(spec, [](const std::string& p) { return std::filesystem::exists(p); });
if (problems.empty()) write_file("aarch64.cmake", rc::deploy::render(spec));
```

**What this does not do.** It writes the file and checks the settings it knows about. It does not run the compiler, which is the one real check: `cmake --toolchain aarch64.cmake` and a look at the result with `file` or `readelf`, which tell you what a binary was built for. It knows one compiler family (a GCC cross compiler with the usual names), not Clang with `--target`, nor a vendor SDK, nor an Android NDK. It does not populate the sysroot, which is the hard part in practice: copying one from the robot and keeping it in step with the robot's image. And, as in lesson 20-01, this repository has **no cross compiler in its continuous integration**, so what is tested is the text and the checks, not that CMake accepts the file.

## What Breaks First

- **A toolchain file edited by hand and copied.** See `E-DEPLOY-0004`.
- **`-march=native` in a cross build.** See `E-DEPLOY-0005`.
- **A library found on the host.** See `E-DEPLOY-0006`.
