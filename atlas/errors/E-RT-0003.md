## Symptom

Every container in the loop is reserved, every buffer is sized at startup, the
code has been read twice, and an allocation counter still reports dozens per
tick.

Or worse: it reports zero on the developer's machine and dozens on the robot,
with the same source.

## Cause

`reserve` reserves the container and not the things inside it, and several types
allocate at a size boundary that is invisible in the source.

Measured, one pass of each loop body:

| loop body | allocations |
|---|---|
| a fixed array | 0 |
| a reserved `vector<double>`, cleared and refilled | 0 |
| a reserved `vector<string>`, the same thing | **64** |
| the same, with strings that fit inside the object | 0 |
| an unreserved vector grown to 4096 | 13 |

The third row is the one that surprises people. `reserve(64)` made room for
sixty four string **objects**. Each of those then went to the heap for its
characters, because the string was longer than the library keeps inside itself.

That limit is an implementation detail:

- 15 characters on libstdc++ and on the Microsoft library,
- 22 on libc++.

`std::function` has the same shape of boundary. A lambda capturing one double
fits inside it on every library this curriculum builds against; three doubles
does not on some of them. So a loop that is allocation free on a laptop can
allocate on a robot with a different standard library, from source nobody
changed.

## Fix

Count on every toolchain you ship to, in a test that runs in CI, rather than
reasoning about it once.

```cpp
rc::test::AllocationCount count;
loop_body();
RC_CHECK(count.none());
```

Then remove what it finds. In order of how often it works:

**Replace `std::string` in the hot path with a fixed array of characters.** A
message with a `char name[24]` allocates never, on every library, and the size
is visible in the source instead of in a library's internals.

**Reuse the container rather than the capacity.** `clear()` keeps a vector's
capacity, which handles the vector; if the elements own memory, keep the
elements too and overwrite them in place.

**Take callables by template parameter rather than in a `std::function`**, in
the places that run every tick. `std::function` is the right tool at a boundary
you cross once and the wrong one inside a loop.

**Preallocate the objects, not just room for them.** That is what
`rc::rt::Pool` is for: N slots built once, handed out by pointer, and nothing
from the heap afterwards.

And do not memorise the boundaries. Write a test that finds them, the way this
lesson's suite does, so the number is discovered on the machine that matters.
