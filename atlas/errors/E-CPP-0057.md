## Symptom

```
error: non-constant condition for static assertion
error: static_assert expression is not an integral constant expression
error: uninitialized variable 'x' in 'constexpr' function
```

A `static_assert`, an array size, a template argument or a `constexpr`
variable will not accept the expression you gave it, and the expression looks
perfectly ordinary.

## Cause

Usually this is good news, and reading it as an obstacle is the mistake.

A constant expression has to be **computable**, and the rules of what is
computable exclude undefined behaviour. At runtime the compiler is entitled to
assume undefined behaviour does not happen, so it compiles the code and
something arbitrary occurs. In a constant expression it cannot assume: it has
to produce the value, and when there is no value to produce it stops.

So the error is frequently a real defect, caught for free, in a place where
every other tool in this curriculum would have missed it.

The four that come up, all demonstrated in lesson 03-11's `checks/`:

| the expression | at runtime | in a constant expression |
| --- | --- | --- |
| signed overflow, `3000 * 1000000` | undefined; 00-04 measured the wrap, 01-13 measured `atoi` giving -1 | compile error |
| an index past the end | undefined; the address sanitizer may catch it | compile error |
| a division by zero | undefined | compile error |
| reading something never written | undefined; **nothing** catches it, see below | compile error |

The last row is the one to remember. Lesson 02-09 measured a struct member
read inside a function it was passed to: no warning on gcc or clang at any
optimisation level, the address sanitizer ran the program clean and printed
the garbage, and the memory sanitizer, which is the tool for this, is clang
only, cannot be combined with the address sanitizer, needs an instrumented
standard library, and missed that case on this machine.

In a constant expression both compilers refuse it outright:

```
gcc:   uninitialized variable 'x' in 'constexpr' function
clang: uninitialized variable in a constexpr function is a C++20 extension
```

Clang's wording is the more useful one. C++20 relaxed the rule so the
declaration is allowed and reading one during constant evaluation is still not
a constant expression, so the error moves rather than disappearing. This
curriculum is C++17, where the declaration is refused.

## Fix

First, check whether the compiler is right. Most of the time it is, and the
fix is to the arithmetic rather than to the `constexpr`.

If the value genuinely is not knowable at compile time, the error is telling
you something different: this expression depends on something that only exists
while the program runs. Then it should not be in a constant expression, and the
question is which part of it you wanted fixed at build time.

```cpp
// Refused, and correctly: input[0] is not known until the program runs.
constexpr std::uint8_t bits = bits_in_byte(input[0]);

// Accepted: the argument is a literal, so the compiler can do the work.
constexpr std::uint8_t bits = bits_in_byte(0xAA);

// Also fine, and says plainly that this one runs at runtime.
const std::uint8_t bits = bits_in_byte(input[0]);
```

The general move is to push what you can into a constant expression precisely
because it is checked there. An index masked to `0xFF` against a 256 entry
table cannot be out of range, and arranging for the compiler to confirm that
is worth more than a comment claiming it.

`E-CPP-0058` is the companion problem: a `constexpr` function that was
evaluated at runtime when you wanted it done at build time.
