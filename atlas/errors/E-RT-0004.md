title: A pool that runs out quietly, or hands the same slot to two callers
match: a pool that runs out says so, and counts it
match: a pool refuses what it did not hand out

## Symptom

Two things that look unrelated and come from the same class.

**Readings stop appearing.** Under load the loop simply produces nothing for a
while, with no error anywhere, and recovers on its own. Nothing is logged
because nothing failed.

**Two parts of the system see the same object.** A value written by one consumer
appears in another's data, or a message is processed twice, or a field changes
between two lines that do not touch it. It happens rarely and never in a
debugger.

## Cause

The first is a pool that was exhausted and returned nothing, with the caller not
checking. A fixed-capacity pool is right, and running out is a real event that
has to be visible: a pool sized for last year's worst case is the first thing a
new feature outgrows.

The second is a slot released twice. The free list then holds the same index
twice, the next two `acquire` calls return the same address, and two owners
write to one object believing they each have their own. The mistake is at the
second release and the damage appears somewhere else entirely, which is what
makes it expensive.

Both have the same underlying shape: **a pool that answers quietly when it
should be answering loudly.**

## Fix

Refuse, and count the refusal.

```cpp
T* acquire() {
  if (available_ == 0) { ++exhaustions_; return nullptr; }
  ...
}

bool release(T* item) {
  if (item == nullptr) return false;
  if (item < storage_.data() || item >= storage_.data() + N) { ++foreign_releases_; return false; }
  if (!used_[slot]) { ++double_releases_; return false; }
  ...
}
```

Three rules that follow.

**Never grow when exhausted.** A pool that allocates under pressure has given up
the only property it had, and it does so at the worst moment, which is exactly
when the system is already late.

**Report the counters, do not only assert them.** `exhaustions()` on a healthy
loop is zero, and the first time it is not is a fact about capacity that
somebody needs. The same for double and foreign releases: those are not
recoverable conditions, they are bugs, and the count is the only evidence they
leave.

**Make the caller handle nothing.** `acquire` returning `nullptr` is an ordinary
outcome that has an answer: drop the sample and count it, reuse the previous
one, or refuse the work. Any of those is better than a null dereference, and all
of them are better than not checking.

Sizing the pool is then a measurement rather than a guess: run the worst case
you can arrange, read `in_use()` at its peak, and take that plus a margin you
can defend.
