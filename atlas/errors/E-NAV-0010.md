id: E-NAV-0010
title: A target search allowed to look backwards along the path
match: a target search that is allowed to look backwards
platforms: linux, windows

## Symptom

A path follower that works on every test path drives straight past a real one,
or turns around and repeats a section it has already done, or locks onto the
start of the route and drives away from everything.

It only happens on paths that come back near themselves: a corridor swept in
both directions, a lap, a mowing pattern, anything with two parallel legs.

## Cause

The follower is choosing its target by searching the path from the beginning.

Written straight from the description of the method, the loop is: find the first
point at least a lookahead away. From a metre along the path, the *start* of the
path is also more than a lookahead away, and it comes first in the array, so
that is what gets chosen.

Measured on a path that runs 8 m out, crosses over, and comes back along a leg
0.6 m away, 20 m long in total:

| search | outcome |
|---|---|
| forward only, from the last target | arrived, 19.34 m driven |
| from the start of the path, every tick | **lost, 80.00 m driven, ending at (80.00, 0.00)** |

The second robot never turned once. A point directly behind it has no sideways
offset, so the curvature is zero, so it drove in a straight line until the test
gave up.

A search for the *nearest* point rather than the first far enough one survives
this particular path, because the robot stays close to the leg it is on. It
fails the same way whenever the robot is displaced far enough that the other leg
is nearer, which is what a shove, a slip or a fresh localisation does.

## Fix

Keep the index of the last target and never search before it.

```cpp
for (std::size_t k = from_; k < path_.size(); ++k) {
  if (distance(path_[k], pose) >= lookahead_) {
    from_ = k > 0 ? k - 1 : 0;
    return k;
  }
}
```

That makes the search monotonic: the target only ever moves forward along the
path, however close two parts of the path come to each other. It is also faster,
because each tick starts where the last one stopped instead of scanning
everything.

Give it a `reset()` for the case where the path is replaced or the robot is
genuinely relocated, and call it there deliberately rather than every tick.

The wider point is about the test path. **A straight line cannot tell a correct
target search from a broken one**, and neither can a single gentle curve. Any
path used to accept a follower needs to come back near itself somewhere, because
that is the shape real routes have and the only shape this bug shows on.
