id: E-NUM-0022
title: Small values added to a large total and discarded
match: adding one a hundred thousand times to a large total changes nothing
platforms: linux, windows
teaches: 01-08-close-enough
---

## Symptom

A running total stops responding. An odometer reads the same after an hour of
driving. An integrator that worked in testing does nothing on a long run. A sum
over a large data set is wrong by an amount suspiciously close to the number of
small elements in it.

Nothing errors, nothing warns, and the arithmetic is exactly what the code
says.

## Cause

Addition discards whatever will not fit in the result, and once the running
total is large enough the increment is below the gap between neighbouring
doubles, so adding it changes nothing at all.

At 1e16 the gap between doubles is 2.0. Adding 1.0 there does not round up or
lose a little, it does nothing: the result is bit for bit the value you started
with.

Measured, one value of 1e16 followed by a hundred thousand values of 1.0:

| order | sum | error |
|---|---|---|
| largest first | 10000000000000000.0 | -100000.0 |
| smallest first | 10000000000100000.0 | 0.0 |
| compensated, largest first | 10000000000100000.0 | 0.0 |

Every one of the hundred thousand additions was discarded. Not rounded,
discarded. The sum is exactly the first value.

This is also why **the order you add numbers in changes the answer**. Floating
point addition is not associative, which means a sum is not a property of a set
of numbers, it is a property of a set of numbers and a traversal order.

## Fix

**Add the small ones together first.** Sorting by magnitude gave the exact
answer above, because the small values accumulate into something large enough
to survive meeting the big one.

**Or compensate.** `rc::core::kahan_sum` keeps what did not fit in a second
variable and feeds it back on the next addition. Four lines, and it got the
exact answer without reordering anything, which matters when the values arrive
one at a time and cannot be sorted.

**Keep the big constant out of the accumulator.** An odometer that accumulates
distance travelled and adds the starting position once at the end never has a
large total to lose increments into. This is usually the real fix for a robot:
integrate the delta, not the absolute.

**Do not write the correction with the parentheses removed.** `(next - total)
- adjusted` is the whole algorithm. Algebraically it is zero; in floating point
it is the lost part. An optimiser permitted to reassociate it, which is what
`-ffast-math` permits, computes zero and silently throws the correction away.

**Reset long running integrators.** Any accumulator that runs for the lifetime
of a machine eventually reaches a magnitude where its own increments are
invisible. Rebasing it periodically costs a line and bounds the problem.
