## Symptom

Handing a `std::packaged_task`, or a lambda that captured a `std::unique_ptr` or a `std::promise`, to
something that takes a `std::function` gives a wall of template text that ends in:

```
error: static assertion failed: std::function target must be copy-constructible         (gcc 11)
error: call to deleted constructor of 'std::packaged_task<int ()>'                      (clang 14)
```

## Cause

`std::function` stores a copy of what it is given and may copy itself, so whatever it holds must be
**copyable**. A `std::packaged_task` owns the shared state behind a future and exists once, so it is
**move-only**. The same goes for a lambda that captures a move-only object by value.

Measured: assigning a `packaged_task` to a `std::function<void()>` was refused by both compilers. The
pool's task type is `std::function<void()>`, so a pool that returns results hits this at once.

## Fix

Share it. Put the move-only object in a `std::shared_ptr` and let the lambda copy the pointer:

```cpp
auto task = std::make_shared<std::packaged_task<int()>>(std::move(fn));
std::future<int> result = task->get_future();
pool.submit([task] { (*task)(); });
```

There is still one task. Every copy of the lambda holds the same pointer, and the last to go destroys it:
if the pool refuses the submission, that is the moment the unrun task is destroyed, and the future then
reports `broken_promise` (`E-THREAD-0021`) instead of waiting for ever.

C++23 has `std::move_only_function`, which takes move-only targets. This curriculum is on C++17, so the
`shared_ptr` is the idiom and the lesson is why it exists.
