id: E-IO-0002
title: A struct sent whole arrives as nonsense
match: a struct is bigger than the data in it
match: sizeof\(Reading\) > kSumOfReadingFields
platforms: linux, windows
teaches: 08-01-bytes-on-the-wire
---

## Symptom

The first field of a received message is right and everything after it is
nonsense. Or the message is the wrong length and the parser is offset by a few
bytes for the rest of the stream. Rebuilding one side with a different compiler,
or a different optimisation level, changes the nonsense.

## Cause

A struct was sent whole:

```cpp
port.write(reinterpret_cast<const char*>(&reading), sizeof(reading));   // the bug
```

`sizeof` is not the sum of the members. For

```cpp
struct Reading {
  std::uint8_t id;       // 1 byte
  double x;              // 8 bytes
  std::uint16_t sequence;// 2 bytes
};
```

eleven bytes of data occupy twenty four, because a `double` must sit at an
address that is a multiple of eight, so the compiler inserts seven bytes of
padding after `id` and pads the end so an array of these stays aligned.
Reordering the fields so the double comes first makes the same data sixteen
bytes.

Three separate things are wrong with sending that:

- **The padding is uninitialised.** Whatever the memory held before is now on
  the wire, which is a correctness problem and, in some settings, a disclosure
  of whatever was in that memory.
- **The layout is a decision, not a fact.** Your compiler chose it with your
  flags for your processor. The device chose differently.
- **The byte order of each field is unstated**, which is `E-IO-0001` arriving at
  the same time.

## Fix

Send fields, never structs. Write each one deliberately, in the order and the
width the protocol specifies:

```cpp
ByteWriter writer(buffer);
writer.put_u8(reading.id);
writer.put_u16(reading.sequence);
writer.put_f32(static_cast<float>(reading.x));
```

Eleven bytes of data become eleven bytes on the wire, in an order you chose and
can point at in the datasheet.

Two things that look like fixes and are not.

`#pragma pack(1)` removes the padding and leaves everything else wrong: the byte
order is still unstated, the field widths are still whatever the compiler says,
and misaligned members are now undefined behaviour to take the address of, which
faults on some ARM cores.

`static_assert(sizeof(Reading) == 11)` turns a silent bug into a build failure
on one compiler and changes nothing about the other three problems. It is worth
having as a guard once fields are being sent properly, and worth nothing as a
substitute.
