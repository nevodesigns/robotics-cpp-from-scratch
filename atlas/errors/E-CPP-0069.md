## Symptom

A function behaves differently after an `#include` or a `using` line was added
elsewhere. It returns a different type, or rounds differently, or no longer runs
code the author put in it, such as a counter, a log line or a range check. There
is no error and no warning.

## Cause

A using-directive makes names visible, and a call goes to whichever visible
function fits **best**. The best fit is not always yours.

Lesson 01-02 wrote `clamp(double, double, double)`. C++17 has `std::clamp` as
well. Measured on gcc 11 and clang 14, a call `clamp(5, 0, 3)` with plain ints:

| | global `clamp(double)` ran | result type |
|---|---|---|
| as written | yes | **double**, 8 bytes |
| after `using namespace std;` | **no** | **int**, 4 bytes |

The ints fit `std::clamp` exactly and the global one only after converting, so the
better match won, and the better match was the function the author did not write.
No warning on either compiler.

The suite reproduces the same shape with a namespace of its own, `general`,
holding an `int` overload, so the measurement does not depend on what a given
standard library contains.

## Fix

Write the prefix, and use the leading `::` when you mean the global one:

```cpp
std::clamp(value, lo, hi);       // the standard one
::clamp(value, lo, hi);          // ours, and nothing a using-directive can redirect
```

A leading `::` is what `drive::limit` uses in this lesson, and it is why a
using-directive somewhere else cannot change which function it calls: the suite
puts one in scope and checks.

Rule L018 forbids `using namespace std;` in every lesson for this reason. It is
not about style. It is that a line which was correct stops being correct when a
library adds a name, and nothing marks the place.
