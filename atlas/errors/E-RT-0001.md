title: A histogram that hides its own tail
match: expected .*worst\(\) to be within
match: expected .*overflows\(\) to equal
match: a stall does not read as the top of the range
platforms: linux, windows
teaches: 07-03-measuring-jitter

## Symptom

A latency histogram looks healthy. The worst case sits neatly at the top of the
range, the percentiles are tidy, and the loop it measures still misses deadlines
in the field.

In lesson 07-03 the test says:

```text
FAIL  a stall does not read as the top of the range
  expected h.worst() to be within 1e-12 of 4000
    expected: 4000
    actual:   100
```

A four millisecond stall was recorded as one hundred microseconds.

## Cause

The index is clamped instead of counted:

```cpp
int index = static_cast<int>(value / bucket_width_);
if (index >= bucket_count_) index = bucket_count_ - 1;  // the bug
buckets_[index] += 1;
```

Clamping keeps the array access in bounds, which is why it looks like defensive
programming and survives review. What it actually does is fold every sample
beyond the range into the last bucket, where it is indistinguishable from a
sample that only just reached the range.

The consequence is specific and bad. A histogram covering zero to one thousand
microseconds reports a worst case of one thousand whether the true worst was
1001 or 40000. The larger the outlier, the more the histogram understates it,
so the instrument fails hardest exactly where the answer matters most.

The same shape appears when the worst value is read back out of the buckets
rather than tracked separately. The buckets only know which range a sample fell
in, so the best they can report is a range edge.

## Fix

Count what is beyond the range, and track the true worst separately.

```cpp
void record(double value) {
  count_ += 1;
  if (value > worst_) worst_ = value;          // exact, not a bucket edge

  if (value < 0.0) { underflows_ += 1; return; }
  const int index = static_cast<int>(value / bucket_width_);
  if (index >= bucket_count_) { overflows_ += 1; return; }   // before the access
  buckets_[index] += 1;
}
```

Three properties follow, and all three are worth stating because each is a way
histograms lie:

- **`overflows()` is reported, not hidden.** A histogram with a non zero
  overflow count is a histogram whose range is too small for what it is
  measuring, and the reader has to be told.
- **`worst()` is a measured value, not a bucket edge.** Bucketing is a summary,
  and the worst case is the one number that must not be summarised.
- **The bounds check comes before the array access**, not after, which is the
  same ordering mistake as `E-CPP-0007` in a different costume.

Choosing the range so overflows stay rare is the other half. If the overflow
count is not small, widen the buckets or add more of them rather than reading
percentiles that describe only the part of the distribution that fit.
