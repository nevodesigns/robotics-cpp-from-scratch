## Symptom

The compiler warns about a line that is correct, and says nothing about a line
that is undefined behaviour. Both in the same project, sometimes in the same
file.

## Cause

A warning is a heuristic about intent, and intent is not always what the code
shape suggests. Three measured cases from this curriculum.

### It warned about the safe thing

```cpp
Pose p = {1.5};   // warning: missing initializer for member 'Pose::y'
```

This is completely defined. Aggregate initialisation value initialises every
member you did not mention, so `p` is `{1.5, 0.0, 0.0}` and not one member set
with two left as leftovers.

The warning is really asking for something else, and the measurement shows it:
give the members default initialisers and the identical brace is silent on
both compilers. So the warning means "I cannot tell whether you meant this",
and the answer is to make the type say so.

Counting it is also compiler dependent. gcc reports it once per missing
member, clang once per brace, so the same file gave gcc 4 warning lines at 3
sites and clang 3 at 3.

### It was silent about the dangerous thing

```cpp
Handle* h = new FileHandle();
delete h;         // undefined behaviour: ~Handle is not virtual
```

`-Wdelete-non-virtual-dtor` catches this **only when the base already has some
other virtual function**, because that is what marks the class as polymorphic.
Measured: both gcc and clang are silent for a base with no virtual functions
at all, which is exactly the shape a handle or a resource wrapper has, and
exactly the case that bites. Lesson 03-10's answer is a `static_assert`
rather than a warning.

### It differed by compiler for a subtle reason

Measured in lesson 01-07: clang suppresses `-Wsign-compare` when the signed
operand is `const`, so adding `const` to a loop bound removed a diagnostic.
Two compilers, one source, and the quieter one was not the safer one.

### And once it was right in a way nobody expected

clang's `-Wunused-lambda-capture` fired on a lambda whose body was only
`sizeof(payload)`. The capture was not required, because `sizeof` is
unevaluated, and the measurement of what a capture costs therefore rested on a
capture the compiler was entitled to drop. Both compilers happened to keep it
and the numbers were identical either way, and the warning was still pointing
at a real defect in the test.

## Fix

Read the warning as a question rather than an instruction.

| the warning says | the question it is really asking |
| --- | --- |
| missing field initializer | can a reader tell you meant the rest to be zero? |
| deleting a polymorphic type with no virtual destructor | is anything ever deleted through this base? |
| unused lambda capture | does your code depend on something it never uses? |

Then answer it in the type or the test, where the answer is permanent, rather
than at the call site, where it has to be repeated.

And do not conclude from silence. A warning that is absent means the compiler
had no heuristic that fired, not that the code is correct. The cases nothing
warns about are in `E-TEST-0015` and lesson 02-09: for those, the tools are a
`static_assert`, a constant expression, or a design that cannot express the
mistake.
