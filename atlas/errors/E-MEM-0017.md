id: E-MEM-0017
title: An allocator measurement that changed under the sanitizer
match: (new-delete-type-mismatch|the freed block did not come back)
platforms: linux, windows
teaches: 04-07-the-tool-that-watches-it-run
---

## Symptom

A test that measures something about the heap passes in one build and fails in
the sanitizer lane, or reports a completely different number there.

Or the reverse, which is worse: it passes in both and you believe a number
that was only true in one of them.

## Cause

The address sanitizer **replaces the allocator**. It is not a passive observer.

Freed blocks go into a quarantine instead of being handed straight back, so a
later allocation of the same size gets different memory. Allocations are
surrounded by poisoned redzones, so the usable block is not adjacent to its
neighbours the way it usually is. Memory is poisoned on the way out, so
nothing you wrote before freeing survives.

Measured on lesson 02-09's heap test, which writes `0x7e` into 32 bytes, frees
them, and asks for 32 bytes again:

| | bytes zero on arrival | bytes still holding the pattern |
| --- | --- | --- |
| no sanitizer | 27 of 32 | **16 of 32** |
| address sanitizer | 0 of 32 | **0 of 32** |

Both numbers are correct. Neither is a fact about C++, and a test that
asserted either one would be asserting a property of a build configuration.

The same instrumentation is why lesson 03-10 cannot demonstrate a missing
virtual destructor at runtime: deleting a derived object through a base
pointer with a non-virtual destructor is reported as
`new-delete-type-mismatch` and the program stops, which is correct of the
sanitizer and useless as a measurement.

## Fix

Ask which build you are in, and say so.

```cpp
#include <rc/test/sanitizer.hpp>

if (rc::test::allocator_measurements_trustworthy()) {
  // the real allocator: the number means something
} else {
  RC_CHECK(recovered == 0u);   // the quarantine: assert that instead
}
```

Because the detection is `constexpr`, the branch costs nothing at runtime: the
compiler keeps one side and removes the other. So a suite can carry both paths
and pay for neither, which is what makes this better than maintaining two
suites or excluding the test from one lane.

The general rule, which applies well beyond the allocator: **a measurement is
of a program plus the thing measuring it.** When the instrumentation changes
the quantity, the test has to name which configuration it is reporting, or it
is publishing a number without saying what it measured.

For what the sanitizers do and do not find at all, see `E-DEBUG-0010` and
lesson 04-07's table: of five common defects, the pair this curriculum's lane
builds with finds three.
