id: E-CPP-0033
title: A guard against overflow that overflows inside the guard
match: the checks never perform the operation they are asking about
platforms: linux, windows
teaches: 01-09-something-not-in-the-program
---

## Symptom

An overflow check is in place, the code looks careful, and the undefined
behaviour sanitizer reports a signed integer overflow inside the checking
function itself.

Or there is no sanitizer, and the guard simply gives the wrong answer for a
handful of inputs near the limits, which are the only inputs it exists for.

## Cause

The check performed the arithmetic it was asking about, or performed different
arithmetic that is also undefined.

Three ways this happens, all of them in checks written carefully.

**Computing the thing first.** `if (a + b > INT_MAX)` has already overflowed by
the time the comparison runs, and `INT_MAX` is the largest int, so the
comparison is also always false.

**Negating to reuse a check.** `subtract_overflows(a, b)` written as
`add_overflows(a, -b)` is undefined when `b` is `INT_MIN`, because `INT_MIN` has
no positive counterpart. The test for this asks whether `1 - INT_MIN`
overflows. It does.

**Dividing to avoid multiplying, and dividing by the wrong thing.** Using
division to answer whether `a * b` overflows is the right technique, and it has
two landmines in it. `b` may be zero, and dividing by zero is undefined.
`INT_MIN / -1` overflows, which is undefined behaviour inside the function
written to prevent undefined behaviour.

The order that works:

```cpp
if (a == 0 || b == 0) return false;     // or the division below divides by it
if (a == -1) return negate_overflows(b);
if (b == -1) return negate_overflows(a);
// every remaining division is in range
```

## Fix

**Rearrange, never compute.** Every one of these checks can be written as a
comparison against a limit with the operands moved to the other side.
`a > INT_MAX - b` and `a + b > INT_MAX` ask the same question, and only one of
them can be asked.

**Order the special cases before the general one.** Zero and minus one first,
then the signs. Each is there because the general case is undefined without it.

**Verify exhaustively against a wider type.** This is cheap and it is the only
way to be sure. Sweep every pair in a window, compute the truth in
`long long`, and compare. Sweep near the limits, not just around zero: a window
of four million pairs centred on zero contains no overflow at all, so a
function that always answers no passes it.

**Run the checks themselves under the sanitizer.** A guard that reaches the
right answer by committing undefined behaviour on the way is reported there and
nowhere else. The lesson's suite runs its whole boundary set under the
undefined behaviour sanitizer for exactly this reason, and a clean run is the
assertion.
