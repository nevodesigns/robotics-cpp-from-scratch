id: E-IO-0025
title: A sequence number that wraps and looks like a jump backwards
match: the counter wrapping is not a loss, and a loss across the wrap is counted
match: expected (wrapped|v).lost to equal
platforms: linux, windows
teaches: 08-08-a-device-faster-than-you-read
---

## Symptom

A stream in perfect order reads as perfect, which is why this goes unseen. Then a
few messages are lost across the point where the counter wraps, and the tracker
reports **no loss** and calls the next two hundred or so messages "late". The
figure clears by itself after the counter has come all the way round.

## Cause

The difference was computed in `int`.

```cpp
int ahead = sequence - expected;   // both are std::uint8_t
```

A `uint8_t` is promoted to `int` before the subtraction, so `2 - 254` is `-252`
and not `4`. In order, the two are always equal and the bug cannot show, which is
why every test on a clean stream passes. It appears only when a loss straddles the
wrap.

Measured, with messages 253 to 256 lost and the stream otherwise in order:

| | lost | called late | in step |
|---|---|---|---|
| the difference taken in `int` | 0 | 252 | 443 |
| the difference taken in the counter's width | 4 | 0 | 695 |

The four lost messages are not counted, and because a late message does not move
the expectation, every message after it is also compared with the old one and
called late until the stream has gone all the way round to catch up.

## Fix

Cast the difference back to the counter's type before comparing it:

```cpp
const T ahead = static_cast<T>(sequence - expected_);
```

`0 - 255` computed that way is `1`, a stream in order reads as in order, and a gap
across the wrap is counted correctly: from 253 to 2 is four missing, 254, 255, 0
and 1.
