## Symptom

An arm commanded to a point it cannot reach does something rather than refusing.
Depending on how the solver was written, either:

- it produces joint angles that put the tool somewhere else entirely, and
  nothing reports a problem, or
- it produces `nan`, which is passed to the joint controllers, and every axis
  behaves unpredictably at once.

The second is more alarming and much easier to find. The first is the one that
ships.

## Cause

Two separate boundaries, and both are easy to forget.

**Too far.** Beyond the sum of the link lengths there is no answer at all.

**Too close.** Inside the difference between them there is a hole the arm cannot
fold into. A 0.5 and 0.3 arm cannot reach anything nearer than 0.2 to its own
shoulder, and targets near the base look innocuous.

Outside either boundary the law of cosines produces an argument outside minus
one to one, and `acos` of that is not a number.

There is a third case, and it is the one that bites hardest, because it happens
at points the arm **can** reach. Right at the boundary, floating point rounding
pushes the argument a fraction past one:

```text
target taken from the arm's own forward kinematics at full extension
argument = 1.00000000000000066613       (1 + 6.7e-16)
acos     = nan
```

Measured across a hundred thousand fully extended configurations, **more than
half** produced an argument above one. Reaching the edge of the workspace is an
ordinary thing for an arm to do, so this is the common case there rather than an
unlucky one.

## Fix

Check the boundaries, with a tolerance, and clamp before `acos`:

```cpp
const double reach = std::hypot(x, y);
const double tolerance = 1e-9;
if (reach > l1 + l2 + tolerance)          return unexpected(ReachError::TooFar);
if (reach < std::fabs(l1 - l2) - tolerance) return unexpected(ReachError::TooClose);

double cos_q2 = (reach * reach - l1 * l1 - l2 * l2) / (2.0 * l1 * l2);
if (cos_q2 > 1.0) cos_q2 = 1.0;
if (cos_q2 < -1.0) cos_q2 = -1.0;
```

Both the tolerance and the clamp are needed, and they do different jobs. The
tolerance stops a point the arm can very nearly touch from being refused. The
clamp stops the arithmetic at a point that was accepted from producing `nan`.

Return the reason rather than a boolean. "Too far" and "too close" call for
different responses from the caller, and a single failure value makes them
indistinguishable at exactly the moment somebody needs to know.

One thing that is **not** a defect, and is worth recognising so it is not
treated as one. Near the boundary the solution changes very fast: measured, a
target moving 0.0099 metres moves the elbow 0.2944 radians, thirty times more.
The solver is correct at both points. That is a singularity, and it is a
planning problem rather than a solver problem.
