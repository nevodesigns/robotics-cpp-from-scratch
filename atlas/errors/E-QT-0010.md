id: E-QT-0010
title: A queued signal argument dropped in silence
match: an argument type Qt cannot queue is dropped in silence
match: Cannot queue arguments of type
platforms: linux, windows
teaches: 09-03-across-the-thread-boundary
---

## Symptom

A sensor thread emits and nothing arrives. The connection was made, the emit is
plainly happening under a debugger, and the slot never runs.

Nothing returns an error. The only evidence is one line on the console, among
whatever else the application prints:

```text
QObject::connect: Cannot queue arguments of type 'Qt::HANDLE'
(Make sure 'Qt::HANDLE' is registered using qRegisterMetaType().)
```

That line is printed once, at connect time, and the program has no way to see
it.

## Cause

A queued connection **copies** its arguments, because the receiving thread reads
them later. Copying means the meta object system has to know the type, by the
name the signal declares it under.

When it does not, Qt makes the connection anyway, drops every delivery, and
warns. Measured in lesson 09-03: a signal carrying `Qt::HANDLE` across a thread
boundary delivered **0 of 100**.

The Qt 5 advice is to call `qRegisterMetaType` for anything you send. On Qt 6
that is mostly obsolete and it is worth knowing why, because the obsolete advice
hides the real hazard. Measured on Qt 6.2, a plain struct crosses a queued
connection **five hundred times out of five hundred** with no
`Q_DECLARE_METATYPE` and no `qRegisterMetaType` at all: a connection made with
the function pointer syntax registers the type itself.

What still fails is a type Qt records under a name it cannot resolve, of which a
typedef like `Qt::HANDLE` is the common example. And whether a particular type
falls on that side is **not portable**. The same signal carrying `Qt::HANDLE`:

| | delivered |
|---|---|
| Linux, Qt 6.2.4 | 0 of 100, with the warning above |
| Windows, Qt 6.5.3 | 100 of 100, silently fine |

`connect` returned true in both cases, and nothing in the program could tell
them apart.

## Fix

Register the name the signal uses:

```cpp
qRegisterMetaType<Qt::HANDLE>("Qt::HANDLE");
```

before the first connection carrying it. With that, the same signal delivers
100 of 100.

The more useful fix is the habit, because this failure mode is not going to
announce itself:

**A connection that was made is not a connection that delivers.** `connect`
returning true means the signatures matched, not that anything will arrive.
Assert that something arrived, in a test, once, for every signal that crosses a
thread.

That is the only advice in this entry that holds on every platform and every Qt
version, which is precisely why it is the one to keep. Reasoning about whether a
type "should" register is not a substitute for looking.

Two things that reduce the surface.

**Send plain value types.** A small struct of numbers is copyable, registers
itself on Qt 6, and does not raise the question. Sending a pointer across a
thread raises a much harder one about who owns it.

**Avoid typedefs in signal signatures.** The meta object system works from the
name written in the header, so `Qt::HANDLE` and `void*` are different names for
the same type and only one of them is registered.
