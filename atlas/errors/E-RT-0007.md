id: E-RT-0007
title: Padding that does not survive contact with a container
match: a padded value takes a whole line, and keeps it inside an array
platforms: linux, windows
teaches: 07-05-two-counters-one-cache-line
---

## Symptom

The struct has padding in it, `sizeof` is checked and is 64, and the false
sharing is still there. Or the padding is present in one build and gone in
another, or present on Linux and gone on Windows.

## Cause

Padding a member is not the same as aligning a type, and only one of them
survives being put in an array.

```cpp
struct Slot {
  std::atomic<long> value;
  char padding[56];              // 64 bytes, and no alignment requirement
};
```

That struct is 64 bytes and can start anywhere. In a `std::vector<Slot>` the
first element may begin part way through a line, so `value` in one element and
`value` in the next can still land together.

```cpp
template <class T>
struct alignas(rc::rt::kCacheLine) Padded {
  T value{};
};
```

That one has both a size and an alignment of 64, so every element of a vector
starts on a line boundary. `alignas` on the type, not on a member and not a
trailing array of chars.

Two related ways the padding disappears:

**Padding by hand with a number.** `char padding[56]` is right for one type on
one platform and silently wrong when the member's size changes. Let the compiler
work it out from the alignment.

**Trusting `sizeof` alone.** It says how far apart two elements are and says
nothing about where the first one starts. Both matter and only `alignas` gives
you both.

## Fix

Assert the property rather than reading the declaration.

```cpp
RC_CHECK_EQ(sizeof(Padded<std::atomic<long>>), rc::rt::kCacheLine);
RC_CHECK_EQ(alignof(Padded<std::atomic<long>>), rc::rt::kCacheLine);

std::vector<Padded<std::atomic<long>>> slots(4);
const char* first = reinterpret_cast<const char*>(&slots[0]);
const char* second = reinterpret_cast<const char*>(&slots[1]);
RC_CHECK_EQ(static_cast<std::size_t>(second - first), rc::rt::kCacheLine);
```

The last three lines are the ones that matter: they check the distance in the
container the code actually uses, which is where the padding was supposed to
apply and where it goes missing.

Over-aligned types in containers are a C++17 guarantee. On an older standard
`operator new` was not required to honour an alignment greater than
`max_align_t`, so the same code compiled and the padding did nothing. If a
project is on C++14 or earlier, that is not a detail, it is the whole bug.
