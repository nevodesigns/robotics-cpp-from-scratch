id: E-CPP-0052
title: The destructor that did not run
match: deleting object of polymorphic class type which has non-virtual destructor
platforms: linux, windows
teaches: 03-10-the-destructor-that-did-not-run
---

## Symptom

A program that holds things behind an interface leaks, and the leak is
proportional to how long it has been running. A sensor stack reopens the same
device every few minutes. A connection pool grows. Memory climbs on a robot
that is doing nothing new.

Under the address sanitizer, the blunt version:

```
ERROR: AddressSanitizer: new-delete-type-mismatch
```

Sometimes a compiler warning, which is the lucky case:

```
warning: deleting object of polymorphic class type 'Handle' which has
non-virtual destructor might cause undefined behavior [-Wdelete-non-virtual-dtor]
```

Frequently nothing at all.

## Cause

```cpp
Sensor* s = new Thermometer(21.5);
delete s;                    // runs ~Sensor, never ~Thermometer
```

`delete` through a pointer to a base calls the base destructor. If that
destructor is not `virtual`, the derived one does not run, so every resource
the derived class owns is simply abandoned. It is undefined behaviour, not
merely wasteful, and the behaviour you get in practice is a partial
destruction and a deallocation of the wrong size.

Measured in lesson 03-10, with a derived class owning one heap string, counted
with replaced global `operator new` and `operator delete`:

| base destructor | allocations still live after `delete` |
| --- | --- |
| not virtual | **2** |
| `virtual` | **0** |

Two, not one, because the string object and the buffer it owns are both lost.

The diagnostic situation is worth knowing exactly, because it decides whether
you can rely on the compiler.

| the base | gcc | clang |
| --- | --- | --- |
| has some other virtual function | warns | warns |
| has no virtual functions at all | **silent** | **silent** |

The second row is the common one for the types this bites: a handle, a
resource wrapper, a little base class someone added to share two fields. Those
have no virtual functions, so nothing marks them as polymorphic, and nothing
warns.

## Fix

```cpp
class Sensor {
 public:
  virtual ~Sensor() = default;
  virtual double read() const = 0;
};
```

One word. It costs one pointer per object, shared with any other virtual
function the class has, and the lesson measures that too: a struct with one
virtual function is eight bytes larger on a 64 bit platform.

Then make it a rule rather than a habit, because this is the trap that cannot
be caught by testing. A test that demonstrates it is a test that performs
undefined behaviour, and the address sanitizer stops the program rather than
reporting a number.

```cpp
#include <type_traits>
static_assert(std::has_virtual_destructor<Sensor>::value,
              "deleted through a base pointer, so this is required");
```

One line per interface, next to the declaration. It turns an afternoon of
hunting into a build failure.

Two cases where you do not need it, and should not pay for it.

**A base nothing is ever deleted through.** If the only way the type is used is
by value, no `delete` ever sees a base pointer. Make that true by construction
rather than by hope: a protected non virtual destructor stops anyone deleting
through the base at all, and is the right answer for a mixin or a policy base.

**A value type.** `rc::math::Pose` has no virtual anything, and neither does
any other value type in `librc`. The three interfaces that do are
`rc::core::Clock`, `rc::io::BytePort` and `rc::io::SensorSource`, and each
opens with the virtual destructor for this reason.
