id: E-NUM-0023
title: A conversion that cannot fail, and therefore cannot tell you
match: atoi returned zero for something that was not a number
platforms: linux, windows
teaches: 01-13-the-argument-that-was-not-there
---

## Symptom

A tool is given a speed and does nothing, reporting success.

A limit typed with a typo becomes a negative number, and the machine runs the
wrong way.

A value of `3.9` is accepted and behaves like `3`.

No error, no warning, no diagnostic. The program ran, returned 0, and did the
wrong thing quietly.

## Cause

`std::atoi` has no way to report a failure. Its return type is `int`, every
`int` is a possible answer, and there is no second channel.

Measured in lesson 01-13, on five strings a user can type into a numeric
option:

| input | `atoi` | `rc::core::parse_number` |
| --- | --- | --- |
| `42` | 42 | accepted |
| `abc` | **0** | refused |
| (empty) | **0** | refused |
| `3.9` | **3** | accepted as 3.9 |
| `7abc` | **7** | refused |

Two of the five are numbers. `parse_number` accepts exactly those two. `atoi`
gets three wrong, in three different ways:

**`0` for things that are not numbers at all**, which is indistinguishable
from a user who deliberately typed 0. For a speed, a gain or a timeout, 0 is
a legitimate value, so there is nothing to detect.

**`3` for `3.9`**, a real number read as a different one, because `atoi` only
ever reads an integer and stops at the dot without comment.

**`7` for `7abc`**, because it stops at the first character it cannot use and
does not consider the rest your problem.

And on a value too large for an `int` it is not merely wrong, it is undefined.
Measured standalone, `atoi("99999999999999999999")` returned **-1**, while
`strtol` on the same string returned `LONG_MAX` and set `errno` to `ERANGE`. A
mistyped speed limit became a negative speed.

`std::stoi` and `std::stod` throw, which is better, but they answer a
different question than the one you asked: they report whether the string
*starts with* a number. Lesson 01-12 measured that, and `std::stod` accepted
all seven of its malformed fields, including `1,5` read as `1`.

## Fix

Use a conversion that has somewhere to put the failure.

```cpp
#include <rc/core/args.hpp>

const rc::core::Arguments::Number speed = args.number("--speed");
if (!speed.present) return usage("--speed is required");
if (!speed.ok)      return usage("--speed needs a number");
drive(speed.value);
```

Three outcomes, kept apart: never given, given with nothing after it, given
with something that is not a number. A function returning a plain `double`
would have to pick one value to mean all three, and the value available is 0.

Underneath, `rc::core::parse_number` uses `strtod` and then insists that the
entire field was consumed, which is the check `stod` leaves out.

If you are working with a C API and `strtol` is what you have, the full
pattern is:

```cpp
errno = 0;
char* end = nullptr;
const long value = std::strtol(text, &end, 10);
const bool ok = *text != '\0' && end != nullptr && *end == '\0' && errno != ERANGE;
```

All four conditions. Dropping the `*end == '\0'` is how `7abc` becomes 7, and
dropping the `errno` check is how a 20 digit number becomes `LONG_MAX`.
