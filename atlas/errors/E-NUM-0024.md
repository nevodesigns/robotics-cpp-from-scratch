id: E-NUM-0024
title: An exit status that was truncated into success
match: the program returned a count and the shell saw zero
platforms: linux, windows
teaches: 00-09-what-the-program-tells-the-outside-world
---

## Symptom

A tool counts the problems it found and returns the count, so a script can see
how bad things were.

The script reports success. Usually not at first, and usually on the worst run
of the week, which is the one with the most problems in it.

```
$ ./check_routes
256 problems found
$ echo $?
0
```

## Cause

`main` returns `int`, and the number that leaves the process is not an `int`.
Only the low eight bits survive, so what a shell sees is your return value
modulo 256.

Measured in lesson 00-09:

| `main` returned | the shell saw |
| --- | --- |
| 0 | 0 |
| 1 | 1 |
| 2 | 2 |
| 255 | 255 |
| **256** | **0** |
| 257 | 1 |
| -1 | 255 |

The fifth row is the defect. `return number_of_failures;` is a natural thing
to write and it reports success at exactly 256 failures, and again at 512, and
at every multiple after that.

This is lesson 00-04's integer truncation in a place nobody looks for it. The
value is not wrapped by C++ and no warning is available, because the
truncation happens when the process ends rather than in any expression the
compiler can see.

A negative return is the same mechanism from the other side: `return -1;`
arrives as 255, which is a failure and so happens to be harmless, but it is
not the number anybody intended.

## Fix

Collapse the count deliberately, and put the count where it can be read.

```cpp
#include <rc/core/exit_status.hpp>

std::cerr << problems << " problem(s) found\n";
return rc::core::status_for(problems);
```

`status_for` returns `kSuccess` for zero and `kFailed` for everything else,
including a negative count, because a count that came out negative is itself a
problem and must not read as everything being fine.

One problem and a thousand problems are the same answer to the only question a
shell asks, which is whether to carry on. The quantity is interesting to a
person, so it belongs in a message on stderr, where it is not truncated and
where it can say what the problems actually were.

If you genuinely need to pass a number out of a process, pass it on stdout as
text and let the caller read it. That is what the number is for, and lesson
01-12's parsing is the other half of it.

**A status above 128 usually means the program did not choose to stop.** A
segmentation fault was seen as 139, which is 128 plus `SIGSEGV`'s 11. So that
range is not yours to use: a tool returning 139 on purpose is indistinguishable
from one that crashed.
