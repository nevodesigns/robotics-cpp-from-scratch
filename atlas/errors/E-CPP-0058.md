## Symptom

A table, a conversion factor or a polynomial was marked `constexpr` so it
would be computed during the build. Startup is still slow, or the generated
code still contains the loop, or a profile still shows the function being
called.

Nothing is wrong and nothing warns. The program is correct. It simply did the
work at the time you were trying to avoid.

## Cause

`constexpr` on a function is **permission, not instruction**. It says the
function is *allowed* to be evaluated during translation if it is used
somewhere that requires a constant. Used anywhere else, it is an ordinary
function and it runs like one.

```cpp
constexpr std::uint8_t bits_in_byte(std::size_t value);

const std::uint8_t a = bits_in_byte(0xAA);   // may run at either time
const std::uint8_t b = bits_in_byte(n);      // runs at runtime, necessarily
```

The first line is the trap. It is permitted to be folded at compile time and
it is permitted not to be, the choice is the implementation's, and nothing in
the source records which happened.

The same applies to the variable, which is where tables usually lose:

```cpp
const std::array<std::uint8_t, 256> table = make_table(...);       // may be built at startup
constexpr std::array<std::uint8_t, 256> table = make_table(...);   // must be built at compile time
```

## Fix

Require the result where only a constant will do, and the compiler has no
choice left.

Any of these forces it: a `constexpr` variable, a `static_assert`, an array
bound, a template argument, an enumerator, a `case` label.

```cpp
constexpr std::array<std::uint8_t, 256> kBitsPerByte =
    rc::core::make_table<std::uint8_t, 256>(bits_in_byte);
```

Written that way, a build that could not do the work at compile time is a
build that fails, which is the guarantee that was wanted.

Note the asymmetry honestly, because it decides how you test this. **You can
prove an evaluation happened at compile time** by putting it where a runtime
value would be refused. **You cannot prove one did not happen**: there is no
portable way to assert that the compiler declined to fold something. So this
is not a property to check in a test. It is a property to require in the
declaration.

Lesson 03-11's suite is written on exactly that line. The compile-time facts
are `constexpr` variables at file scope, which compile only if the compiler
could work the values out, and the values themselves are checked at runtime.
Putting the values in `static_assert` instead would have meant an unfinished
exercise could not be built at all, and a suite that cannot run tells a
learner nothing about which function to write.

In C++20 there is `consteval` for a function that must always be evaluated at
compile time, and `constinit` for a variable that must be initialised without
runtime work. This curriculum is C++17, where the `constexpr` variable is the
way to insist.
