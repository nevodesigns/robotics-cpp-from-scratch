title: A storage comparison that compared only the address
match: reserving first means nothing moves at all
platforms: linux, windows

## Symptom

A check written to detect reallocation reports that nothing moved, when
something did. A test asserting that a control loop performs no allocation
passes while the loop is allocating.

```cpp
const void* before = samples.data();
step();
assert(samples.data() == before);     // passes anyway
```

## Cause

An allocator is free to hand a freed block straight back for the next request
of the same size, and frequently does, because that is the cheapest thing it
can do.

So a vector that reallocated may land at the address it just released. The
elements were copied, every borrowed pointer was invalidated, the work was
done, and the address is identical.

A vector that shrank and grew again can do the same. So can one that was
cleared and refilled.

The repair is to compare something that changes when the buffer changes.
Capacity does: a reallocation that produces the same capacity would have had no
reason to happen.

```cpp
struct StorageId {
  const void* data;
  std::size_t capacity;
};
```

Measured, with both fields compared: twenty insertions after reserving for
twenty reported the storage unchanged, and every reallocation in a thousand
insertion run was detected, with no prediction wrong.

## Fix

**Compare the identity, not the address.** `rc::core::storage_of` captures both
fields and `rc::core::same_storage` compares both.

**Prefer predicting to detecting.** `rc::core::would_reallocate(samples, n)`
answers the question before the insertion, from the size and the capacity,
without depending on what the allocator chose to do. A prediction cannot be
fooled by an address being reused.

**Assert on capacity in a no allocation test.** A control loop that must not
allocate should assert that capacity did not change, which is a stronger and
simpler claim than anything about addresses. `rc/test/leak_check.hpp` counts
allocations directly and is the right tool when you need the number.

**Do not reason about allocator behaviour.** Whether a freed block comes back
is not specified, varies between platforms, and changes with the size of the
request. Any check that depends on it is a check that will pass on your machine
and fail in the field, or the reverse.
