id: E-CPP-0053
title: The derived part that was thrown away
match: passing a derived object to a parameter taken by value
platforms: linux, windows
teaches: 03-10-the-destructor-that-did-not-run
---

## Symptom

A function that should see a thermometer sees a sensor. The number it reads is
the base class default, usually `0`, which is a plausible reading and so
survives review.

Nothing fails. No exception, no crash, no warning, no diagnostic available to
switch on. The call compiles and runs and gives the wrong answer.

Often it appears when a container is involved: `std::vector<Sensor>` filled
with thermometers behaves as though every element is a plain sensor.

## Cause

```cpp
double read_a_copy(Sensor s) { return s.read(); }   // by value
```

The parameter is a `Sensor`, so the copy made for the call is `sizeof(Sensor)`
bytes. The derived part has nowhere to go and is not copied. This is slicing,
and it is entirely legal: the function asked for a `Sensor` and it got one.

Measured in lesson 03-10 on the same object:

| how it was passed | what `read()` returned |
| --- | --- |
| `const LooseSensor&` | **21.5** |
| `LooseSensor` by value | **0** |

And the sizes that explain it, on a 64 bit platform:

| type | bytes |
| --- | --- |
| `LooseSensor` | 8 |
| `LooseThermometer` | 16 |

The copy is eight bytes. The object was sixteen. Virtual dispatch then works
correctly on the copy, which really is a `LooseSensor`, and returns the base
implementation.

Neither gcc 11 nor clang 14 warns about this at any optimisation level, and
clang is silent even under `-Weverything`.

## Fix

Make the copy unavailable, in the base, once.

```cpp
class Sensor {
 public:
  virtual ~Sensor() = default;
  Sensor(const Sensor&) = delete;
  Sensor& operator=(const Sensor&) = delete;
  virtual double read() const = 0;
 protected:
  Sensor() = default;
};
```

Now the by value parameter is a compile error rather than a wrong number, and
the error points at the call. Nothing is lost by this, because copying an
interface has no sensible meaning: the only reason the type is an interface is
that what is behind it varies.

The protected constructor is the companion move. An interface is not something
you instantiate on its own, and making the constructor protected says so.

At the call sites, pass `const Sensor&` for something you only read during the
call, and hold `std::unique_ptr<Sensor>` for something you own. A container of
polymorphic things is a container of pointers, `std::vector<std::unique_ptr<Sensor>>`,
never a container of values, for exactly this reason.

If you genuinely need a copy of the real object, the usual answer is a virtual
`clone()` returning `std::unique_ptr<Sensor>`, which puts the decision in the
derived class that knows what it is.
