title: A fault check that reports no fault, because of operator precedence
match: the precedence mistake reports the wrong fault, quietly
platforms: linux, windows
teaches: 01-10-the-fault-that-never-fired

## Symptom

A driver never reports a fault the hardware is plainly signalling. The status
register read back from the device has the right bits in it, printing it shows
the fault, and the branch that acts on it is never taken.

```cpp
if (status & kOverTemp != 0) { shut_down(); }   // never fires
```

Or worse, it works for one fault and not the others, which sends everybody
looking at the device instead of at the line.

## Cause

`==` and `!=` bind tighter than `&`. So that line parses as

```cpp
if (status & (kOverTemp != 0))
```

`kOverTemp != 0` is true, which converts to 1, so the whole expression is
`status & 1`. It asks whether **bit zero** is set, whatever flag you named.

Measured with over temperature and stalled both set, so the fault is certainly
there:

| form | result |
|---|---|
| `has_any(status, kOverTemp)` | true |
| `status & kOverTemp != 0`, which is `status & 1` | 0, so false |

The reason this survives testing is the part worth remembering: **it is not
always wrong.** When the flag being tested happens to be bit zero, the mistaken
form agrees with the correct one. The first flag in a data sheet is usually bit
zero, so the first test anybody writes passes.

gcc and clang both refuse it under `-Werror` through `-Wparentheses`. That is
worth having switched on, and lesson 01-07 measured how uneven that kind of
coverage is between compilers, so it is not something to rely on alone.

## Fix

**Use a named function.** `rc::core::has_any(status, kOverTemp)` has no
precedence to get wrong, which is the entire reason the header exists.

**If you write it inline, bracket the and.** `(status & kOverTemp) != 0`. The
brackets are not decoration, they are the fix.

**Drop the comparison.** `if (status & kOverTemp)` is correct, because the
result converts to bool on its own. It is also one character away from the bug,
so the named function is still better.

**Switch on `-Wparentheses`,** which is in `-Wall` on gcc and clang. It is free
and it catches this one.

**Test a flag that is not bit zero.** A suite that only ever checks the first
flag cannot distinguish the right expression from the wrong one.
