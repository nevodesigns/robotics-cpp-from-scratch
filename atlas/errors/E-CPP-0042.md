id: E-CPP-0042
title: A history buffer that allocates on every reading
match: a ring allocates nothing, ever
platforms: linux, windows
teaches: 03-07-one-template-many-types
---

## Symptom

A control loop that holds a window of recent readings misses its deadline
occasionally and unpredictably. The arithmetic is trivial. A latency histogram
has a long tail that does not correspond to anything the loop does.

```cpp
history.push_back(reading);
if (history.size() > window) history.erase(history.begin());
```

## Cause

Two separate costs, in two lines.

`push_back` may reallocate, which allocates a buffer, copies every element and
frees the old one, in a loop that is supposed to be bounded.
`erase(history.begin())` shifts every remaining element down by one, every
single cycle, and invalidates every pointer into the buffer, which is
`E-MEM-0012`.

Neither is visible in the arithmetic, and both are proportional to the window
rather than constant.

A fixed capacity ring buffer has neither. The capacity is a compile time
constant, so the storage is an array inside the object. Measured, 1000 pushes
into a `Ring<double, 64>`:

| | |
|---|---|
| allocations | **0 blocks, 0 arrays** |
| `sizeof(Ring<double, 64>)` | 528 bytes, of which 512 are the doubles |

The remaining 16 bytes are two indices. Nothing is on the heap, nothing is
copied on a push, and nothing shifts.

## Fix

**Use a fixed capacity container for a fixed size window.**
`rc::core::Ring<double, 64>` says the size in the type, allocates nothing, and
overwrites the oldest element in constant time.

**If the window must be chosen at runtime, allocate once.** Reserve a
`std::vector` to its final capacity at construction and index into it yourself
with the same modular arithmetic. `rc::core::reserve_for` from lesson 02-07 is
the tool, and the point is that the allocation happens before the loop starts.

**Never erase from the front of a vector in a loop.** If you find yourself
doing it, the container is wrong for the job. `std::deque` has
`pop_front` in constant time and is the right answer when the size is genuinely
unbounded.

**Count the allocations rather than reasoning about them.**
`rc::test::AllocationCount` from lesson 02-02 is four lines in a test and turns
"this should not allocate" into an assertion. A loop that must not allocate
should say so in a test, because nothing else will notice when it starts.

**Watch for the same bug in a string.** Building a log line per cycle with
`operator+` allocates, and lesson 01-11 measured when a string's characters
stop fitting inside the object.
