## Symptom

The interface loads. Nothing errors. A panel is the wrong size, or a gauge sits
at zero, or a button is invisible because its width is nought.

Changing the QML changes nothing, because the property being edited is not the
one in play. Reading the file, everything looks right.

## Cause

A binding referred to a name that does not exist, so it evaluated to undefined,
so the property kept its default.

QML did not refuse the file. It could not: whether `robto.speed` resolves is not
knowable by reading the document, only by running the binding in the context the
engine happens to have. So the file loads, the object is created, the interface
draws, and the property is zero.

The one trace is a line on stderr from `QQmlEngine`, and in a running
application nobody is watching stderr.

Measured with the lesson's cases, all three loaded successfully:

| case | loaded | warnings | width |
|---|---|---|---|
| a name that does not exist | yes | 1 | 0 |
| a typo on a context property | yes | 1 | 0 |
| a binding loop | yes | 1 | 2 |

And through the ordinary API, the file with the undefined name gives a component
whose `status()` is `Ready`, whose `errors()` is empty, and whose root object has
a width of zero. Every question you can think to ask says it is fine.

## Fix

**Connect `QQmlEngine::warnings`.** It exists, it carries a `QList<QQmlError>`
with a line and a column, and nothing is connected to it until you connect it.
That one connection is the whole difference between this failure being
invisible and being a number you can assert on.

```cpp
QObject::connect(&engine, &QQmlEngine::warnings, &sink,
                 [&](const QList<QQmlError>& reported) { ... });
```

**Fail a test when the count is not zero.** A warning during load is not a
diagnostic to read later, it is a defect. `rc::qt::QmlHost::warning_count()`
exists so a test can say so.

**Prefer a typed context object to loose context properties.** A
`setContextProperty("robot", &object)` with `Q_PROPERTY` members gives QML
something whose property names are checked when the binding runs, and a typo on
the object name still fails silently. Neither is a compiler, and that is the
point: nothing here is checked at build time, so the check has to be a test.

**Assert the values, not the load.** The load succeeding tells you almost
nothing. What tells you something is that the width is 100 because the file says
100.
