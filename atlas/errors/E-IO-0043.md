## Symptom

The telemetry has gaps, and the gaps line up with commands. Every time the program
asks the device something, a frame or two of the stream goes missing. The loss
counter is steady between commands and jumps when one is sent, and it is worst when
the device is slow to answer.

## Cause

A link carries two kinds of message and something has to decide where each goes. The
simple request waits for its answer by polling the link in a loop, and the loop
discards everything that is not the answer it is waiting for. Every telemetry frame
that arrives during the wait is read out of the port and thrown away, and the
telemetry loop never sees it.

Measured, fifty requests made while a 100 Hz stream runs on the same link:

| | telemetry lost |
|---|---|
| waiting by polling the link and discarding the rest | 38 |
| a session, which routes each message to who wants it | 0 |

Each request waits a few milliseconds, and a frame arrives every ten, so about one
frame in each wait is eaten. The reverse also happens: a telemetry loop that polls
first and ignores a type it does not know discards the answers.

## Fix

Exactly one place reads the link, and it routes. A message is offered to the
requester first, which takes it if it is a response, whether or not it is the one
being waited for, and returns whether it did:

```cpp
if (requester_->handle(message)) continue;
if (message.size() == 9 && message[0] == kTelemetryType) accept_telemetry(message, now);
```

The requester never polls. `begin`, `handle` and `tick` are all it has, so it cannot
read what is not its own.
