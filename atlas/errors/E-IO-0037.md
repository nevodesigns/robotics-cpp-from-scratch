id: E-IO-0037
title: A duration of minus a minute, once every wrap
match: a duration across the wrap is ten milliseconds, not minus a minute
match: a sixteen bit tick counter is followed through its wrap without a jump
match: expected .*naive.* to equal -65526
platforms: linux, windows
teaches: 08-12-the-devices-own-clock
---

## Symptom

Once in a while, with no pattern anyone can find, a velocity, a rate or a
derivative is nonsense for one frame: a speed of zero, a spike, a negative time
step in the log. With a device that stamps in milliseconds on sixteen bits it
happens every 65.5 seconds, which is a rate nobody notices in a hand test and
everybody notices in a ten minute run.

## Cause

Two stamps on opposite sides of the wrap, subtracted in `int`:

```cpp
int dt = now_stamp - last_stamp;     // both are std::uint16_t
```

A `uint16_t` is promoted to `int` before the subtraction, so 5 minus 65531 is
`-65526` and not `10`. Measured, a centimetre of travel in ten milliseconds, stamped
65531 then 5:

| | duration | speed |
|---|---|---|
| subtracted in int | -65526 ms | -0.00015 m/s |
| unwrapped | 10 ms | 1.00 m/s |

The wrong speed is not noise: it is a clean number, small and plausible, and so it
passes any sanity check except the one that matters.

## Fix

Take the difference in the counter's own width and widen only afterwards:

```cpp
const std::uint16_t forward = static_cast<std::uint16_t>(raw - last);
total += forward;      // a 64 bit running total that does not wrap
```

and compute every duration from the running total. A thirty two bit counter wraps
the same way, in 49.7 days at a millisecond, which is long enough that the code has
never been tried across it. The test runs it there on purpose.
