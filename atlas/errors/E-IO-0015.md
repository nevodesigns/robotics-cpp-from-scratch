id: E-IO-0015
title: A row that parsed perfectly and had the wrong number of columns
match: a whole log, counted rather than silently filtered
platforms: linux, windows
teaches: 01-12-readings-from-somewhere-else
---

## Symptom

A log loads, every field is a valid number, and the columns are wrong from
some point onwards. A timestamp column is read as a velocity. A plot has one
spike in it. An analysis that worked on last week's file fails on this week's
with no error of any kind.

## Cause

Checking each field cannot catch a row of the wrong shape, because every field
in it is fine.

Two lines in a real log do this, and both of them parse without complaint.

**A row cut short** when the logger was killed. `0.2,1.60` in a three column
file is a perfectly good two column row.

**A decimal comma in a comma separated file.** `0.4,1,70,2.45` splits into
four fields and every one of them is a number. Nothing about it is malformed
at the field level at all; it is simply one column too wide.

Measured on a log with three bad lines in it: **one** was caught by parsing a
field, and **two** were caught only by counting columns.

Which means a reader that validates fields and not shape reports a clean load
and hands back rows of mixed width, and whatever indexes column 2 afterwards
gets a different quantity depending on the row.

## Fix

**Decide the width and enforce it.** `rc::core::read_log` takes the width from
the first usable row, so a caller does not have to know it in advance and a
file that is consistently four columns is read as four columns.

```cpp
if (report.width == 0) report.width = row.values.size();
if (row.values.size() != report.width) { ++report.wrong_width; continue; }
```

**Count the two kinds separately.** A file with unparsable fields has a sensor
problem. A file with wrong width rows has a format problem, and frequently a
locale problem. Reporting one number for both leaves the reader guessing which.

**Report the first bad line, one based, counting every line in the file.**
Including the blanks and comments, because that is what an editor shows and
the point of the number is that somebody can go and look.

**Suspect the separator when the width is one too many.** A file whose rows
are consistently one column wider than the header is a file written with a
decimal comma, and the fix is to read it with a semicolon separator rather than
to patch the rows.

**Never return only the rows that worked.** A reader that silently filters
cannot be distinguished from one that found nothing wrong, and the difference
between two bad lines and two thousand is the difference between a glitch and
a format mismatch.
