id: E-VIS-0001
title: A straight line that comes back as a diagonal
match: a straight line read with the wrong stride is a diagonal
match: a view reads nothing outside the picture
platforms: linux, windows
teaches: 15-05-an-image-is-a-buffer

## Symptom

An image sheared into a diagonal, or repeating stripes, or the whole picture
leaning. Sometimes it looks like the frame arrived corrupted; sometimes it looks
like an interlacing problem; sometimes only the right hand edge is wrong.

The same code is fine on one camera and wrong on another, or fine at one
resolution and wrong at a different one.

## Cause

The distance from one row to the next is not the width.

Rows are padded so that each begins at an address the hardware likes, usually a
multiple of four or of the cache line, so a frame 13 pixels wide arrives with 16
bytes per row. Indexing by width then reads three bytes further left on every
row, and the error accumulates down the image.

A vertical line at column 10, in a 13 by 8 frame with a stride of 16:

```
read with the stride the buffer has, 16     read as though the stride were 13

  ..........#..                               ..........#..
  ..........#..                               .............
  ..........#..                               #............
  ..........#..                               ...#.........
  ..........#..                               ......#......
  ..........#..                               .........#...
  ..........#..                               ............#
  ..........#..                               .............
```

| row | true column | as read |
|---|---|---|
| 0 | 10 | **10** |
| 1 | 10 | none |
| 2 | 10 | 0 |
| 3 | 10 | 3 |
| 4 | 10 | 6 |

**The first row is right.** That is the whole difficulty. A test on one row
passes, a test on a frame whose width happens to be a multiple of four passes,
and every camera in the office might be one of those.

## Fix

Carry the stride with the pointer and never compute an index without it.

```cpp
struct Gray8 {
  std::uint8_t* data = nullptr;
  int width = 0, height = 0, stride = 0;

  std::uint8_t at(int x, int y) const {
    if (!inside(x, y)) return 0;
    return data[static_cast<std::size_t>(y) * stride + x];
  }
};
```

Three details in those few lines.

**Get the stride from the source**, every frame. `bytesPerLine`, `linesize`,
`step`, `rowPitch`: every library has one and every one of them can change
between frames when a format or a resolution changes.

**Bounds check.** An index built from a wrong stride runs off the end of the
last row, and the bytes after a frame belong to whoever allocated next. Reading
them is a crash on a good day.

**Cast to `std::size_t` before multiplying.** A 4000 by 3000 frame is twelve
million pixels; `y * stride` in `int` overflows on a larger one, and signed
overflow is undefined rather than merely wrong.

And test with a width that needs padding. A frame 13 or 17 or 30 pixels wide
finds this in one run; 640 by 480 never will.
