## Symptom

The marker is out of view, or covered, or the light has failed, and the vision
reports finding it. Confidently, in the middle of the frame. The robot drives at
the centre of whatever it is looking at.

Or the reverse: a single hot pixel on the sensor is reported as the marker, and
the robot drives at that.

## Cause

An automatic threshold answers where to split and not whether there is anything
to split.

On an evenly lit wall, every pixel 90:

| | |
|---|---|
| Otsu says | **0** |
| blobs found | 1 |
| pixels in it | **200 of 200** |

With no two groups to separate, the best split is at the bottom of the range and
every pixel is above it. The failure is not that it finds nothing. It finds
**everything**, as one blob covering the frame, whose centre is the middle of
the picture, which looks exactly like a marker sitting straight ahead.

At the other end of the same problem, one bright pixel on an otherwise flat
image is also a perfectly good blob, of one pixel.

## Fix

The threshold is a step, not an answer. Something after it has to decide whether
what came back is the thing you were looking for.

**Check what fraction of the frame came back.**

```cpp
const double fraction = double(blob.pixels) / (image.width * image.height);
if (fraction > 0.5) return NotFound{};   // that is the room, not the marker
```

One division, and it catches the empty scene, the covered lens, the lights
going out and the exposure running away.

**Give the object a size range**, in pixels, from how large it is and how far
away it can be. A blob of one pixel and a blob of half the frame are both
rejected by the same two comparisons, and a size range is not an optimisation:
it is part of saying what you are looking for.

**Check the separation the threshold achieved.** Otsu already computes how far
apart the two groups are; a split with almost no gap between the groups is a
split of noise. Keeping that number and putting a floor under it rejects the
flat wall before any blob is found at all.

**And have a way to say no.** The function's return type should be able to
express "nothing here", and the caller should have to handle it, exactly as with
the sensor in `E-SENSE-0012`. A vision routine that always returns a position is
a vision routine that will one day return a wrong one with no way to tell.
