id: E-RT-0006
title: Half a fix for false sharing, which is no fix
match: padding and caching are worth little apart and a lot together
platforms: linux, windows
teaches: 07-05-two-counters-one-cache-line
---

## Symptom

The false sharing was found and fixed, the two indices were moved onto separate
cache lines, and the benchmark barely moved. Or the opposite: the shared index
was cached in a local so it is read far less often, and that barely moved
either.

Both changes are obviously right and neither one shows up.

## Cause

There were two reasons the line kept moving between the cores, and each fix
removes one of them.

A single producer, single consumer queue has the producer read the consumer's
index on every push, to see whether there is room. So:

- **Padding without caching.** The indices are on separate lines and the
  producer still reads the consumer's line on every single operation. The line
  still moves.
- **Caching without padding.** The producer reads its cached copy instead, and
  the cached copy sits in the same line as the index the consumer writes, so it
  is invalidated about as often as the real one would have been read. The line
  still moves.

Measured over four runs of four million items through a 1024 slot queue:

| change | worth |
|---|---|
| a line apart, index read every time | 1 to 6 percent |
| adjacent, index cached | -8 to +14 percent |
| **both** | **76, 77, 83 and 95 percent** |

Each alone is inside the run-to-run noise. Together they roughly double the
throughput.

## Fix

Do both, and understand them as one change: **the other thread's line must be
neither shared nor read.**

```cpp
if (next == cached_head_) {
  cached_head_ = head_.value.load(std::memory_order_acquire);
  if (next == cached_head_) return false;
}
```

Consult the cached copy; go and look only when the cached value says stop; and
believe the fresh value if it says stop too. The producer then reads the
consumer's line only when the queue is genuinely full, which on a healthy system
is never.

Then place the cached copy beside the index its own thread writes, not beside
the one it caches:

```cpp
Padded<std::atomic<std::size_t>> head_;
std::size_t cached_tail_ = 0;   // consumer only
Padded<std::atomic<std::size_t>> tail_;
std::size_t cached_head_ = 0;   // producer only
```

The producer touches `tail_` and `cached_head_`; the consumer touches `head_`
and `cached_tail_`; the two sets never meet.

The general lesson is worth more than the queue. **When a fix that is obviously
correct produces no measurable improvement, the usual reason is that something
else is producing the same effect**, and removing one of two causes leaves the
symptom exactly where it was. Measure the combinations, not the changes.
