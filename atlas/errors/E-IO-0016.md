title: A reader that takes a filename, and a test that cannot reach it
match: the same reader, on a real file on disk
platforms: linux, windows

## Symptom

The log parsing is untested, because testing it means putting files on disk,
and the tests that do exist are slow, leave rubbish behind when they fail, and
cannot easily cover a file with one bad line in the middle.

```cpp
LogReport read_log(const std::string& path, char separator);
```

So the parsing gets tested through the one sample file somebody committed, and
the twenty interesting malformed cases never get written.

## Cause

The function asked for a filename when what it needed was the contents.

A filename ties the parsing to the filesystem. Every test then needs a
fixture file, a path that works on both Linux and Windows, and a cleanup that
runs even when the test fails. Writing twenty of those is enough work that
nobody writes the twentieth, and the twentieth is the one with the carriage
returns in it.

## Fix

**Take a stream.**

```cpp
LogReport read_log(std::istream& input, char separator);
```

A test hands it a `std::istringstream` holding exactly the awkward content it
wants to exercise, in one line, with no file and no cleanup. A program hands it
a `std::ifstream`. Neither knows about the other.

This is the same idea as the replay sensor in lesson 05-02 and the injectable
clock in 03-05: depend on the interface, not on the device. It is the single
most useful habit in this curriculum for making things testable.

**Keep one test that uses a real file.** The stream tests prove the parsing;
one test that writes a file, reads it back and deletes it proves the other end
is connected. Lesson 01-12 does exactly that, four lines of file against five
tests of strings.

**Open the file at the caller.** The caller knows whether a missing file is
fatal, whether to look in a second place, and what to say about it. A parser
that opens files has opinions about all three and is wrong about at least one.

**Do not take a `std::string` of the whole contents instead.** That works and
it reads the entire file into memory first, which is fine for a log of a
thousand lines and not for one from an eight hour run.
