## Symptom

A control loop meant to run at a real time priority works on a developer's machine and misses deadlines on the robot, or the other way
round. Nothing is logged. A call to set the priority returned a nonzero value that nobody read.

```
sched_setscheduler(SCHED_FIFO, 10): refused: Operation not permitted
```

## Cause

An ordinary process may not raise its own priority. Measured, unprivileged, on Linux:

| request | result |
|---|---|
| `sched_setscheduler(0, SCHED_FIFO, priority 10)` | refused, `Operation not permitted` |
| `nice(-5)`, a higher priority | refused, `Operation not permitted` |
| the range of `SCHED_FIFO` priorities | 1 to 99 |

Real time priorities need a privilege: root, `CAP_SYS_NICE`, or an `RLIMIT_RTPRIO` that was raised for the user. Someone sets it up
when the robot is installed, and a lesson cannot assume it. The call fails quietly, because a priority is a request, and a program
that does not look at the result runs at ordinary priority and thinks it does not.

## Fix

Check the return value and say so:

```cpp
sched_param parameters{};
parameters.sched_priority = 10;
if (sched_setscheduler(0, SCHED_FIFO, &parameters) != 0)
  std::cerr << "no real time priority: " << std::strerror(errno) << ", running at ordinary priority\n";
```

and make it a visible startup fact, a log line or a status the operator sees, since the loop's timing depends on it. Grant the privilege
where the robot is installed (`setcap cap_sys_nice+ep`, or a limits file) and not in the program.

A loop whose deadlines depend on a priority it may not have must measure its own lateness, as lesson 07-03 does, and treat a missed
priority as a fault and not a detail.
