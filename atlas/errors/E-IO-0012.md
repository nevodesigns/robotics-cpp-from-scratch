id: E-IO-0012
title: A serial read that blocks
match: an idle port reads zero, not an error
platforms: linux, windows
teaches: 08-05-opening-a-real-port
---

## Symptom

The program stops. Not a crash and not an error: the control loop simply does
not run again. A debugger attached to it shows the thread inside `read`, or
inside `ReadFile`, and it has been there for minutes.

It began when the device stopped transmitting, so the first suspicion is the
device, and the device is beside the point.

## Cause

The read was asked to wait. On POSIX that is `VMIN`:

| VMIN | VTIME | a read returns |
|---|---|---|
| 0 | 0 | immediately, with whatever is there, possibly nothing |
| n | 0 | when n bytes have arrived, however long that takes |
| 0 | t | when a byte arrives, or after t tenths of a second |
| n | t | when n bytes arrive, or t tenths after the first |

Only the first row is safe for a polled link. Every other row hands a device the
ability to hold your control loop, and a device that has crashed holds it for
ever.

There is a common route to this that looks careful. The port is opened with
`O_NONBLOCK` to stop the open waiting for carrier detect, and the flag is then
cleared because it "was only needed for the open". After that `VMIN` decides,
and a `VMIN` of one blocks.

On Windows the equivalent is leaving `COMMTIMEOUTS` at its defaults, which is a
read that waits indefinitely.

## Fix

Ask for a read that returns what is there and nothing more:

```cpp
settings.c_cc[VMIN] = 0;
settings.c_cc[VTIME] = 0;
```

and on Windows, the documented combination for the same thing:

```cpp
COMMTIMEOUTS timeouts{};
timeouts.ReadIntervalTimeout = MAXDWORD;
timeouts.ReadTotalTimeoutMultiplier = 0;
timeouts.ReadTotalTimeoutConstant = 0;
```

Then treat "nothing arrived" as an ordinary outcome rather than an error, which
is `E-IO-0008`, and decide whether the link is dead from elapsed time without a
valid message, which is `E-IO-0010`. Those three together are what a link needs:
a read that never waits, a zero that is not a failure, and a clock that knows
the difference between a quiet device and an absent one.

One practical note on finding this. A blocking read does not make a test fail,
it makes a test **hang**, and a suite that hangs reports nothing at all. Run
test suites under a timeout, so this shows up as a timeout naming the test
rather than as a build that never finishes.
