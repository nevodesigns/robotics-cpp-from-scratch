id: E-CPP-0043
title: A lambda that captured a copy when it needed the original
match: by value takes a copy now, by reference reads it later
platforms: linux, windows
teaches: 02-08-behaviour-as-a-value
---

## Symptom

A threshold, gain or limit is changed at runtime and the code that checks
against it carries on using the old value. Turning a dial in the interface
changes the number everywhere it is displayed and nowhere it is used.

Or the reverse: a callback stored at startup reads a value that has since been
changed by something unrelated, and nobody can work out who changed it.

```cpp
double limit = configured_limit();
auto too_fast = [limit](double speed) { return speed > limit; };
limit = new_limit_from_operator();      // too_fast does not notice
```

## Cause

The capture list is an ownership decision, and the two forms answer different
questions.

**By value** takes a copy when the lambda is created, and the lambda owns it.
It is a decision taken once.

**By reference** stores somewhere to look, and reads the value at every call.
It is a question asked every time.

Measured, with both created while the limit was 1.0 and then the limit changed
to 100.0, asking whether 50 exceeds it:

| capture | answer |
|---|---|
| `[limit]` by value | **true**, still answering against 1.0 |
| `[&limit]` by reference | false, answering against 100.0 |

Neither is wrong. They are different things, and the one character of
difference between them is easy to read past.

## Fix

**Decide which question you are asking, and say so at the capture.** A limit
somebody can turn wants a reference or a pointer to the owner. A limit that
should be frozen at the moment the callback was registered wants a copy, and the
copy makes that explicit.

**Prefer naming each capture over `[=]` or `[&]`.** Writing `[limit]` or
`[&limit]` is one word longer and says exactly what the lambda depends on. A
catch all capture list means a reader has to scan the body to find out, and it
silently picks up anything a later edit happens to reference.

**Never use `[&]` on a lambda that outlives the scope it was written in.** That
is `E-CPP-0044`.

**Capture a `const` copy when you mean frozen.** A by value capture is already
const inside the lambda unless you write `mutable`, which the checks directory
of lesson 02-08 demonstrates, so the default is on your side here.

**If the value lives in an object, capture `this` or a pointer to it
deliberately.** Then the lifetime question is about the object rather than about
a loose double, and it is a question you already know how to answer from phases
02-03 and 02-04.
