title: A default that stood in for three different answers
match: a fallback returned for an option the user got wrong
platforms: linux, windows

## Symptom

A tool silently uses its default instead of what the user asked for, and the
user has no way to tell. Three different mistakes produce the same silence:

```
drive --speed            # forgot the value
drive --speed=           # typed the = and stopped
drive --sped 0.9         # misspelled the name
```

All three run. All three drive at the default. The third is the one that
causes an argument, because the user is certain they set the speed and the
log says otherwise.

## Cause

The lookup is written to return a value, with a default for "not found":

```cpp
std::string flag_value(const Args& args, const std::string& flag,
                       const std::string& fallback) {
  for (std::size_t i = 0; i < args.size(); ++i) {
    if (args[i] == flag && i + 1 < args.size()) return args[i + 1];
    if (starts_with(args[i], flag + "=")) return args[i].substr(flag.size() + 1);
  }
  return fallback;
}
```

That is this repository's own `tools/rcpp/main.cpp`, and it is why lesson
01-13 exists. It is the shape nearly everyone writes first, and it has one
return channel for four distinct situations:

| what the user did | what comes back |
| --- | --- |
| did not mention the option | the fallback |
| misspelled the option | the fallback |
| gave the option with nothing after it | the fallback |
| gave the option properly | their value |

The first is someone who does not care, and giving them the default is
correct. The second and third are someone who cares and typed it wrong, and
giving them the default is the wrong thing to do: they should be told.

A signature returning one value cannot tell them, no matter how carefully the
body is written. The information is destroyed at the return statement.

## Fix

Return the outcomes, not a value.

```cpp
struct Option {
  bool present = false;    // the name appeared
  bool has_value = false;  // and something followed it
  std::string_view value;
};
```

Then the call site has to say which question it is asking, and the compiler
will not let it pretend otherwise:

```cpp
const rc::core::Option mode = args.option("--mode");
if (mode.present && !mode.has_value) return usage("--mode needs a value");
const std::string_view chosen = mode.has_value ? mode.value : "normal";
```

`rc::core::Option` and `rc::core::Arguments::Number` deliberately have no
conversion to `bool` or to `double`, and the lesson's `checks/` directory
proves both refusals compile-fail. Without that, the first tired afternoon
puts `if (args.option("--mode"))` back into the code and the three answers
collapse again.

The misspelling is the one case this does not catch, because no amount of
return type tells you that `--sped` was meant to be `--speed`. Two things
help, and both are cheap:

**Reject unknown options.** Walk the arguments once, compare each one that
starts with a dash against the list the tool knows, and fail on anything
left over. A tool that accepts `--sped` silently is a tool that will.

**Print what it decided.** One line of the resolved settings, before the work
starts, turns an argument about what was typed into something anybody can
read off the log.
