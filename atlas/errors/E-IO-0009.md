id: E-IO-0009
title: A partial write left unfinished
match: a write that accepts one byte at a time
match: a port that accepts nothing fails the send
platforms: linux, windows
teaches: 08-04-the-link-that-goes-quiet
---

## Symptom

Most commands get through. Occasionally one does not, and when one does not, the
next few are wrong as well rather than merely missing. The failures cluster
under load, when several messages go out close together, and cannot be
reproduced by sending the same command slowly.

## Cause

The return value of `write` was ignored:

```cpp
port.write(frame.data(), frame.size());      // the bug
```

`write` returns how many bytes it accepted, and it is allowed to accept fewer
than it was given: the kernel's buffer was nearly full, the device is not
draining it, the frame was larger than one transfer.

What goes out is a **truncated frame**, and that is worse than a missing one.
A frame that never arrives costs one message. A frame that arrives half finished
costs the receiver its place in the stream: it either waits for payload bytes
that will never come, consuming the beginning of the next real frame while it
waits, or resynchronises onto a byte in the middle of something and produces
garbage that may still pass a weak checksum.

That is why the failures cluster. The first truncated write breaks the next few
frames too.

## Fix

Loop until it is all gone.

```cpp
std::size_t sent = 0;
for (int attempt = 0; attempt < kMaxAttempts && sent < bytes.size(); ++attempt) {
  const int wrote = port.write(rc::span<const std::uint8_t>(
      bytes.data() + sent, bytes.size() - sent));
  if (wrote < 0) { ++port_errors_; return false; }
  if (wrote == 0) continue;              // the buffer was full, try again
  sent += static_cast<std::size_t>(wrote);
}
return sent == bytes.size();
```

Three things that loop gets right.

**A return of zero is not an error**, it is back pressure, and it deserves
another attempt rather than a failure.

**Running out of attempts is reported**, not swallowed. A partial success is the
one outcome the caller must not be told is a success, because the damage is at
the far end where the caller cannot see it.

**The attempt count is bounded**, so a device that has stopped draining its
buffer cannot hold a control loop for ever. What to do when the bound is reached
is a policy question: usually drop the message and count it, because a command
that is late enough is worse than one that never went.
