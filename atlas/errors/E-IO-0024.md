id: E-IO-0024
title: A second frame that waits for a byte that may never come
match: two whole frames hidden inside one false claim are both found
match: required frames.size\(\) to equal
platforms: linux, windows
teaches: 08-07-rescan-instead-of-giving-up
---

## Symptom

The last frame before a pause arrives late, or does not arrive until the device
sends something else. At a steady stream nobody notices. On a device that sends a
burst and goes quiet, the final message of every burst is delivered when the next
burst starts, which looks like a latency of seconds.

## Cause

A rescan can uncover more than one frame in bytes already held. A false claim of
36 bytes may contain two real frames inside it. The parser finds the first and
returns it, and the second is sitting complete in the window.

If the only way to look at the window again is to push another byte, the second
frame waits for one. On a stream that never stops that is a delay of a byte. On
one that goes quiet it is a delay of however long the quiet lasts.

## Fix

Give the parser a way to look again **without** a new byte, and make the caller
use it:

```cpp
bool ready = parser.push(byte);
while (ready) {
  deliver(parser.payload());
  ready = parser.next();      // the window may hold another whole frame
}
```

`next()` runs the same search over what is already held. It returns false the
moment the window holds only an unfinished frame, so the loop ends.
