id: E-CPP-0054
title: An override that overrides nothing
match: marked override, but does not override
platforms: linux, windows
teaches: 03-10-the-destructor-that-did-not-run
---

## Symptom

A derived class defines the function. The base version runs anyway.

Which one runs depends on what sort of reference is in hand, which is the
detail that makes this expensive to find: through a `Sensor&` the base version
runs, through a `Thermometer&` the derived one does, and the same object gives
two different answers in two different functions of the same program.

If `override` is present, a clear error instead:

```
error: 'double Thermometer::read()' marked 'override', but does not override
error: non-virtual member function marked 'override' hides virtual member function
```

## Cause

The signature does not match the one it means to replace. Overriding requires
the name, the parameter types, the constness and the reference qualification
to agree exactly. Any difference produces a new, unrelated function that
merely hides the base one.

The usual near misses, in rough order of frequency:

| base | derived | what happened |
| --- | --- | --- |
| `double read() const` | `double read()` | `const` dropped |
| `void set(const Pose&)` | `void set(Pose)` | parameter by value |
| `double read() const` | `float read() const` | return type differs |
| `void step(double dt)` | `void step(float dt)` | parameter type differs |
| `virtual ~Sensor()` | `~Thermometer()` | the destructor, which also needs it |

The `const` one is the most common by a distance, because it reads correctly
in both places and the difference is one word at the end of a line.

Without `override`, none of these is an error. The derived function is a
perfectly legal new member, so the compiler has nothing to object to. It
cannot know which of the two you meant.

## Fix

Write `override` on every function that is meant to replace a base one, with
no exceptions, including destructors.

```cpp
class Thermometer : public Sensor {
 public:
  ~Thermometer() override { }
  double read() const override { return celsius_; }
  const char* name() const override { return "thermometer"; }
};
```

The keyword adds no runtime cost and no code. It asks the compiler to check
that the function it is attached to really does override something, and every
near miss above becomes an error at the declaration rather than a divergence
at some call site.

Two related habits that come from the same place.

**Drop `virtual` on the derived declarations.** `override` already implies it,
and writing both invites the reader to check which one is load bearing. The
base says `virtual`, the derived says `override`, and the two words then mean
two different things in two different places.

**Use `final` where a class or a function is not meant to be extended
further.** It is the same kind of statement, checked the same way, and it lets
a compiler devirtualise a call it can prove is the last one.
