id: E-CPP-0031
title: A check for overflow that runs after the overflow
match: the predictions are exactly right, everywhere it is swept
platforms: linux, windows
teaches: 01-09-something-not-in-the-program
---

## Symptom

A guard against integer overflow does not fire. The code is obviously correct
and the overflow obviously happens.

```cpp
int total = a + b;
if (total < a) { return too_big(); }   // never taken
```

It works in a debug build and stops working when optimisation is turned on,
or it works on one compiler and not another, or it worked until an unrelated
function nearby was edited.

## Cause

Signed overflow is undefined behaviour, so the compiler is entitled to assume
it does not happen, and it optimises on that assumption.

If `b` is positive, then `a + b` is greater than `a`, unless it overflowed. The
compiler is allowed to assume it did not, so `total < a` is provably false and
the branch is dead code, and dead code is removed.

This is not a bug in the compiler. It is the bargain the language makes: it
will produce fast code, and in exchange you promise never to overflow.

Measured, with a loop doubling an int from 1 while `i > 0`, bounded at 200 so
it could be reported at all:

| build | doublings counted |
|---|---|
| g++ -O0 | 31 |
| g++ -O1 | 31 |
| g++ -O2 | **201, the bound** |
| clang -O2 | **201, the bound** |

At -O2 both compilers removed the exit test. Without the bound the loop does
not end. The source did not change between those rows.

Separately, a function returning `x + 1 > x` called with `INT_MAX` returned
true on both compilers at every optimisation level, which is wrong for the only
value it was asked about.

## Fix

**Ask before, not after.** The question has an answer while both operands are
still ordinary numbers, and no answer afterwards.

```cpp
if (rc::core::add_overflows(a, b)) return too_big();
int total = a + b;                       // now provably safe
```

**Rearrange so the arithmetic stays in range.** `a > INT_MAX - b` answers the
same question as `a + b > INT_MAX` and cannot itself overflow. That is the
whole technique and it is three lines.

**Do not write `subtract_overflows` as `add_overflows(a, -b)`.** Negating
`INT_MIN` is undefined, so that version has the defect inside the check.

**Run the sanitizer lane.** The undefined behaviour sanitizer finds these at
runtime on the paths your tests exercise, and names the operation, the file and
the line. It is the only tool that will tell you, because the compiler is
assuming the problem away rather than reporting it.

**Use a wider type when you can.** If the values fit in `std::int64_t`, doing
the arithmetic there and range checking the result once is simpler than four
predicates and is often the right answer.
