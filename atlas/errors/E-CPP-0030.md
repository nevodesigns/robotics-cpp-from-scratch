id: E-CPP-0030
title: A size put into an int, quietly
match: a size that does not survive being put in an int
platforms: linux, windows
teaches: 01-07-the-loop-that-never-ends

## Symptom

Code that has worked for years fails on a larger input. A count comes back
negative, a loop runs zero times over a full container, or a buffer is allocated
at a fraction of the size asked for.

```cpp
int count = cloud.size();
```

## Cause

`std::size_t` is 64 bits on the machines this curriculum targets and `int` is
32. Assigning one to the other is a narrowing conversion, and it compiles
silently: `-Wall -Wextra` says nothing, on gcc and on clang. `-Wconversion`
reports it and almost nobody switches it on, because it also reports several
hundred conversions that are fine.

The largest size an `int` can hold is 2147483647. One more reading than that and
the value stored is not the size, and on most implementations it is negative.

This is harmless for a hundred readings, harmless for a hundred thousand, and
not harmless for a point cloud or a long log, and nothing at the call site
distinguishes the three.

## Fix

**Keep sizes in a type that can hold them.** `std::ptrdiff_t` through
`rc::core::ssize` is signed, is the same width as `std::size_t` on these
platforms, and is what index arithmetic wants anyway.

**Check when you genuinely must convert.** A C API that takes an `int` length is
a real constraint, and `rc::core::fits_in_int` turns the assumption into a
question that gets answered:

```cpp
if (!rc::core::fits_in_int(cloud.size())) return too_many_points();
```

**Do not reach for `auto` to dodge it.** `auto count = cloud.size();` is
correct here, and it hides the type at exactly the moment the type is the
subject, so the next person writing `count - 1` gets the wrap in
`E-CPP-0028` instead.

**Test at the boundary, not in the middle.** A test with three readings proves
nothing about this. A test that asks whether `INT_MAX + 1` fits takes one line
and does not need the memory to hold it.
