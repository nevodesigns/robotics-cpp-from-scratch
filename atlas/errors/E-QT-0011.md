id: E-QT-0011
title: A direct connection across a thread boundary
match: across threads the slot runs on the receiver's thread
match: two sensors on two threads both reach one log
platforms: linux, windows
teaches: 09-03-across-the-thread-boundary
---

## Symptom

Data arrives, the numbers are right, and the application misbehaves in ways that
do not look related to threading: a widget that repaints at the wrong moment, an
occasional crash inside Qt with a stack nobody wrote, a container that is
sometimes empty when it plainly should not be.

It works for a long time. Under a debugger, with everything slowed down, it
usually works perfectly.

## Cause

The connection was made with `Qt::DirectConnection` across a thread boundary.

A direct connection is a function call. The slot runs **on the thread that
emitted the signal**, immediately, and Qt does not intervene. So an object that
belongs to the main thread has just had one of its methods run on a worker
thread, and everything it touches has been touched from the wrong place.

Measured in lesson 09-03: with a direct connection, the slot's own view of which
thread it is on is the worker's, not the receiver's. With Qt's default it is the
receiver's, which is the entire point.

For a widget this is undefined behaviour rather than a race to reason about. A
`QWidget` may only be touched from the thread that owns it, and the symptoms are
whatever the paint machinery happens to be doing at the time.

## Fix

Leave the default, and say you meant it:

```cpp
QObject::connect(sensor, &Sensor::reading, log, &Log::take, Qt::AutoConnection);
```

`AutoConnection` decides at emit time. Same thread means a direct call and costs
nothing. Different threads means the argument is copied and posted to the
receiver's event loop, so the slot runs where the receiver lives.

That is almost always what you want, and writing it out is worth the line in
code whose whole purpose is which thread things happen on.

Two neighbouring facts worth having.

**Nothing is delivered while the receiver's event loop is not running.** A
queued delivery is an event posted to that loop. A receiver whose loop is
blocked has not lost the readings and has not received them either: they are
waiting. That is the shape of a great many bugs that look like a dead sensor.

**Affinity belongs to the object, not to the connection.** `moveToThread` on the
sensor is what puts it on the worker; nothing about the connection changes, and
neither object has to be told about the other's thread.

`Qt::DirectConnection` across threads is occasionally correct, when the slot
touches nothing that belongs to the receiver and you have thought about it. It
is worth a comment saying so, because the next reader will assume it is this
bug.
