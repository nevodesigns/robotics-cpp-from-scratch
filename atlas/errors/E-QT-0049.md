title: A latest value that does not say how many writes it replaced
match: ten thousand writes before the loop runs are one update, with the newest value and a count of what it replaced
match: a write after a delivery needs a new delivery, and each update counts only what came since the last
platforms: linux, windows
teaches: 09-13-the-signal-sent-ten-thousand-times
---

## Symptom

An interface that shows only the latest reading cannot tell a sensor that stopped from one that is fast: a number that stays the same looks the same either way. Or a coalescing flag that is never cleared and the display freezes after the first update.

## Cause

Keeping only the newest value loses the others silently. If the count of writes is not kept with it, nothing can say that a value replaced nine thousand others, and the loss cannot be checked. And a flag for "a delivery is waiting" must be cleared when the delivery runs, or a write after it never posts another.

Measured: 10000 writes before the loop were **1** update with the value 9999 and **9999** skipped. Three writes, two and one, each followed by the loop, were **3** updates that skipped **2**, **1** and **0**.

## Fix

Count every write, remember how many the last update covered, and clear the pending flag in the delivery:

```cpp
pending_ = false;                       // a write from now on needs a new delivery
skipped = published_ - seen_ - 1;
seen_ = published_;
```
