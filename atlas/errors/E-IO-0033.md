id: E-IO-0033
title: A reader thread that outlives what it reads, or hands over half a message
match: stopping is prompt, is safe twice, and leaves the port alone afterwards
match: latest is never torn while the device is sending
platforms: linux, windows
teaches: 08-10-a-reader-thread-of-its-own
---

## Symptom

Two different failures that share a cause.

At exit, or when a reader is replaced, the program crashes, or hangs, or reports a
use after free in a function that has nothing to do with the destructor. It happens
rarely and more on a loaded machine.

Or the newest message occasionally has the header of one frame and the body of
another. Never when anyone is watching, and the checksum was fine, because the
frame was good and the copy was not.

## Cause

**The thread started before what it uses, or ended after it.** Members are built in
the order they are declared and destroyed in the reverse. A thread declared first
starts running before the queue and the link it uses exist, and a thread that is
not joined until its own destructor body runs may be reading members that are
already gone. The thread must be the **last** member: it starts when everything it
touches exists and is joined, by the compiler, before any of it is destroyed.

And joining needs asking first. A destructor that waits for a thread nobody told to
stop waits for ever.

**The newest message was shared as a plain struct.** Two threads, one writing and
one copying, with nothing between them. A struct of sixty four bytes is not copied
in one step, so the reader can take the first half of one write and the second half
of the next. This is the torn read of lesson 07-01, arriving through a different
door, and it is a data race, which makes the behaviour undefined and not merely
unlucky.

## Fix

Declare the thread last and ask it to stop before it is joined:

```cpp
~LinkReader() { stop(); }       // request_stop, then join

// ... every member the thread uses is declared above this line
rc::rt::ScopedThread thread_;
```

and publish the newest through a `Seqlock`, which hands the reader a whole value or
makes it retry. Measured, with the device sending 1200 frames while the main thread
looked at the newest in a tight loop, 1881086 looks found no torn message and none
that went backwards.
