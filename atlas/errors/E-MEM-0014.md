title: A value that was never written
match: is used uninitialized
platforms: linux, windows

## Symptom

Any of these, and they are the same defect:

The number is wrong, and it is wrong differently each run. Or it is wrong the
same way every run, which is worse, because it looks deliberate.

It works in the debug build and fails in the release build. Or it works in the
release build and fails in the debug build. Both directions happen, and which
one you get is not a property of your code.

It works until you add an unrelated local variable to a function higher up the
call stack.

A heading that should be 0.75 reads as `1.9e-322`, or as `0`, which is a
heading of due north and steers the robot.

Sometimes a diagnostic, which is the lucky case:

```
warning: 'x' is used uninitialized [-Wuninitialized]
warning: 'p.Pose::heading' is used uninitialized [-Wuninitialized]
```

## Cause

Declaring a variable reserves storage. It does not put anything in it. What is
in it is whatever was in that memory before, which is the previous call's
locals if it is on the stack, or the last owner's data and the allocator's
bookkeeping if it is on the heap.

Reading one is undefined behaviour, and that word is doing real work here. The
compiler is permitted to assume it does not happen, so an optimiser may
propagate a constant through the read, delete the branch that depended on it,
or keep the whole variable in a register that was holding something else. This
is why the same source gives one answer at `-O0` and another at `-O2`.

Measured in lesson 02-09: the identical function returning an unwritten `int`
gave `1405118043` compiled at `-O0` and `0` at `-O2`, on one machine with one
compiler. Neither number is a bug in the compiler. There was no correct answer
to give.

Where the diagnostics stop is worth knowing, because it decides how much you
can delegate. Measured with gcc 11 and clang 14 at both `-O0` and `-O2`:

| the read | gcc | clang |
| --- | --- | --- |
| a local `int` read in the same function | warns | warns |
| a struct member read in the same function | warns | silent |
| a struct member read inside a function it was passed to | silent | silent |

The third row is the one that reaches production, and nothing warns about it.

The sanitizers do not cover the gap either. The address sanitizer finds
overflows, leaks and use after free, and it is blind to this: the lesson's
example ran clean under `-fsanitize=address,undefined` and printed the garbage.
The tool that does find it is the memory sanitizer, which is clang only, cannot
be combined with the address sanitizer, and needs the whole program including
the standard library instrumented to be reliable. Tried on this curriculum's
machine, it caught the trivial local and missed the struct member.

## Fix

Initialise at the point of declaration, and prefer making it impossible to
forget over remembering.

**Give members defaults in the type.** This is lesson 01-01's advice and it
pays twice: `Pose p;` becomes a real pose at the origin, and the partial brace
`Pose p = {1.5};` stops warning, because the compiler can see the rest are
written.

```cpp
struct Pose {
  double x = 0.0;
  double y = 0.0;
  double heading = 0.0;
};
```

**Know which forms write and which do not.**

| written | not written |
| --- | --- |
| `Pose p = {};` | `Pose p;` |
| `Pose p = {1.5};`, rest zeroed | |
| `new int[4]()` | `new int[4]` |
| `std::vector<int> v(4)` | |

Braces check the count in one direction only: too many initialisers is an
error everywhere, too few is accepted and the rest are set to zero. So a short
brace is the fix, not a smaller version of the problem.

**Make the storage loud when you cannot avoid the gap.** `rc/core/init.hpp`
fills it with a pattern whose double is a NaN, which propagates through every
operation and compares false against everything, so the bad value appears in a
log instead of steering something. See `E-MEM-0016` for the output parameter
version of the same move.

Note what that does to the rules and not only to the bytes: after the fill,
every byte has been written, so the read is ordinary defined behaviour that
produces a NaN. It does not make the bug legal. It turns a read the optimiser
was entitled to invent an answer for into one you can see.
