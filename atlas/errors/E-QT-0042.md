title: A timer re-armed in its handler runs slower than its period
match: a timer re-armed in its handler for 10 ms ticks every 13 when the handler takes 3
match: expected this to be true: rearmed_ticks
platforms: linux, windows
teaches: 09-11-the-timer-that-fell-behind

## Symptom

A loop meant to run at 100 Hz runs at 77. Nothing is wrong with any one tick: each is on time for the timer that was armed before it. The count of ticks in a minute is short, and the shortfall grows with the work each tick does.

## Cause

A single shot timer started with `start(10)` at the end of the handler means "10 ms from now", and now is after the work. Each cycle is the work plus 10 ms, so the period is whatever the handler took plus the interval, and the error is added up and never given back.

Measured, for 300 ms with a 10 ms interval and a handler that takes 3 ms: the re-armed timer ticked **22** times, where 30 slots of 10 ms went by. A grid ticker in the same loop reached slot **30**.

## Fix

Aim at a time on a grid, not at an interval from now:

```cpp
const long long ms = delay_to_next_ms(0, period_ns, clock.nsecsElapsed());   // the time left in this slot, after the work
timer.start(static_cast<int>(ms));
```
