title: The argument that was not there
match: basic_string::_M_construct null not valid

## Symptom

A tool works when you give it the argument and aborts when you forget it.

```
terminate called after throwing an instance of 'std::logic_error'
  what():  basic_string::_M_construct null not valid
Aborted (core dumped)
```

Or it segfaults with no message at all. Or, on a different standard library,
it prints something that is not a filename and carries on.

## Cause

```cpp
int main(int argc, char** argv) {
  const std::string path = argv[1];     // nothing checked argc
```

The standard guarantees that `argv[argc]` is a null pointer. So on a command
line with no arguments, `argc` is 1 and `argv[1]` is that guaranteed null.

This is worth being precise about, because the instinct is that the read is
out of bounds and it is not. The read is perfectly valid and returns a null
pointer, which is in one way worse: a wild pointer usually crashes where the
mistake is, and a null that looks like a value travels.

Constructing a `std::string` from it is undefined behaviour. Measured on this
curriculum's libstdc++, that specific undefined behaviour happens to be
pleasant: a `std::logic_error` naming the problem, and an abort. That is luck,
not a guarantee. Another implementation may read from address zero, and a
`const char*` passed straight through to a C API will do whatever that API
does with null.

## Fix

Check the count before the index, every time.

```cpp
if (argc < 2) {
  std::cerr << "usage: " << (argc > 0 ? argv[0] : "plan_path") << " <route.csv>\n";
  return 2;
}
```

Note `argc > 0` guarding `argv[0]` as well. It is conventionally the program
name and it is not guaranteed to be there: a process started through some
`exec` calls can have `argc` of 0.

Better, read the command line once into something that cannot be indexed
wrongly:

```cpp
#include <rc/core/args.hpp>

const rc::core::Arguments args(argc, argv);
if (args.size() < 1) return usage(args.program());
```

`rc::core::Arguments` stops at `argc` and at a null entry, so neither a short
`argv` nor a wrong `argc` walks off the end, and an out of range index gives
an empty view rather than undefined behaviour. A tool reading its own
arguments should not be able to fall over on a command line the user did not
type.

The related trap, which has no diagnostic at all: the strings `argv` points at
live as long as the process, so a `std::string_view` of one is safe for the
life of the program. That is not true of a view of a temporary
`std::string`, which dangles immediately. `E-MEM-0001` is that case and
lesson 02-07 is the full account.
