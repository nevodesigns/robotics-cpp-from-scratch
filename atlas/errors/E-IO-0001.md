id: E-IO-0001
title: The bytes arrive in the wrong order
match: expected .*storage\[0\].*to equal
match: most significant byte first
match: expected 16909060
platforms: linux, windows
teaches: 08-01-bytes-on-the-wire
---

## Symptom

Numbers arrive transformed rather than corrupted, which is the clue. A sequence
number of 1000 reads as 59395. A temperature of 0x01020304 reads as 0x04030201,
which is 67305985 instead of 16909060.

Round tripping through your own code is perfect. Only the device disagrees.

In lesson 08-01 the test says:

```text
FAIL  sixteen bits go out most significant byte first
  expected static_cast<int>(storage[0]) to equal 0x01
    got:      2
    expected: 1
```

## Cause

The encoder wrote the memory of the value rather than the value:

```cpp
std::memcpy(out + written, &value, 2);   // the bug
```

That copies the two bytes in whatever order this processor stores them, which on
x86 and on most ARM is least significant first. The protocol asked for most
significant first, and nothing in the code says which one it produced.

The reason it survives every test you write is that a decoder built the same way
reverses it again. Two backwards halves agree with each other perfectly, and the
first thing that disagrees is the device, at the end of a cable, days later.

## Fix

Shift the value instead of copying its memory:

```cpp
out[written++] = static_cast<std::uint8_t>((value >> 8) & 0xFFu);
out[written++] = static_cast<std::uint8_t>((value     ) & 0xFFu);
```

A shift is arithmetic on a number. It means the same thing on a big endian
machine, a little endian machine, and a machine nobody has built yet. Code
written this way has no endianness at all, which is a stronger property than
having the right one.

Do not reach for `htons`, `ntohl` and their family for this. They are not
portable to Windows without extra headers and linking, and they hide the
question rather than answering it: the byte order of the wire is part of the
protocol and belongs written down in the encoder where somebody reading it can
check it against the datasheet.

Then test the bytes, not the round trip. A test that writes a value and reads it
back passes with the order reversed at both ends, which is the failure this
entry exists for. Pin the actual bytes:

```cpp
RC_CHECK_EQ(static_cast<int>(storage[0]), 0x01);
RC_CHECK_EQ(static_cast<int>(storage[1]), 0x02);
```
