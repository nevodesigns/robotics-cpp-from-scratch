title: Reading the wrong side of an optional or an expected

## Symptom

The program stops with bad_optional_access or bad_expected_access, or an
assertion fires saying value was called on something holding an error. Under the
compatibility type in this curriculum it is an assertion with that wording.

## Cause

The result was used without asking which side it holds. An optional that is empty
has no value to give, and an expected that holds an error has no value either.
The type is doing exactly its job by refusing.

## Fix

Ask first. Both types convert to bool, so the check reads naturally:

```cpp
const auto parsed = parse_setting(line);
if (parsed) {
  apply(parsed.value());
} else {
  report(describe(parsed.error()));
}
```

When a default is genuinely correct, value_or says so in one line and cannot be
forgotten:

```cpp
const double hz = find_setting(settings, "loop_hz").value_or(100.0);
```

Reaching for value_or everywhere is its own mistake: a default that nobody chose
is how a robot ends up running at a speed that appears in no configuration file.
