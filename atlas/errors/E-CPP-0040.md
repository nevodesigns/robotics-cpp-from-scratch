id: E-CPP-0040
title: A template error reported from inside a standard library header
match: one template, three types, and no code written twice
platforms: linux, windows
teaches: 03-07-one-template-many-types
---

## Symptom

A hundred lines of error, or two hundred, for one wrong call. The first message
names a file you have never opened, somewhere under `/usr/include/c++`, and
quotes code you did not write. Somewhere in the middle is a chain of "required
from here" lines, and the last one of those is your call site.

```cpp
std::vector<Reading> readings = collect();
std::sort(readings.begin(), readings.end());    // Reading has no operator<
```

## Cause

A template has no declared interface. It is checked against whatever its body
happens to use, so an unsuitable type fails wherever the body first touches
something that type lacks, which is often several layers down inside somebody
else's header.

Measured, on exactly the call above:

| | gcc | clang |
|---|---|---|
| no constraint | 113 lines, 12884 chars | 224 lines, 24069 chars |
| constrained with a trait | 5 lines, 509 chars | 254 lines, 25648 chars |

The unconstrained error's first line names
`/usr/include/c++/11/bits/predefined_ops.h`, **21 instantiation frames** deep.

Read that table carefully, because the obvious conclusion is half wrong. gcc
stops at the failed assertion and the diagnostic collapses to five lines. clang
reports the assertion and then instantiates the rest anyway, so the total
volume goes **up**.

What a constraint reliably fixes on both compilers is the **first error line**,
which becomes a sentence you wrote, naming your own file.

## Fix

**Read the first error.** This is the single most useful habit with templates,
and lesson 00-03 is where it was introduced. Everything after the first error
is usually the compiler explaining how it got there.

**Find your own file in the "required from" chain.** The deepest frame is the
library's problem; the shallowest one in your own code is yours, and that is
the line to change.

**Constrain at your own boundary.**

```cpp
template <class T, std::size_t Capacity>
double average(const Ring<T, Capacity>& ring) {
  static_assert(std::is_arithmetic<T>::value,
                "average() needs numbers. Ring<double, N> or Ring<int, N> work. "
                "For your own type, average the member you mean.");
```

The assertion goes in **your** template, at the edge of your code, so the error
names your file. Putting it deeper does not help, because deeper is where the
problem already was.

**Write the message as an instruction, not a complaint.** "needs numbers, pass
int or double" tells the reader what to do. "T must satisfy Arithmetic" tells
them what the compiler thinks. The first line is the one that gets read, so
spend the sentence on the fix.

**Prefer a trait you already have.** `<type_traits>` has
`std::is_arithmetic`, `std::is_integral`, `std::is_same` and more, and any of
them is cheaper than hand rolling a detection idiom in C++17.
