id: E-IO-0022
title: A parser that throws away the frame it just checked
match: a dropped byte costs one frame, not two
match: a frame that lost a byte does not take the next frame with it
match: expected this to be true: .*lost_per_drop
platforms: linux, windows
teaches: 08-07-rescan-instead-of-giving-up
---

## Symptom

A link that loses one byte in a hundred loses about two frames in a hundred. The
checksum is doing its job and the counters show failures, but the lost frames
are nearly double the lost bytes. Nothing is wrong on a clean cable, so nothing
is wrong in any test.

## Cause

When a checksum fails the parser discards the whole candidate frame, and that is
the mistake. The candidate was built from a length the sender wrote, and if a
byte vanished the candidate reached forward into the **next** frame and took its
start byte. Throwing the candidate away throws away the start of a frame that was
perfectly good.

Measured over fifty thousand frames, one byte in 500 dropped:

| parser | dropped | lost frames | lost per drop |
|---|---|---|---|
| discard the candidate | 1144 | 2158 | 1.89 |
| give up the start byte and look again | 1144 | 1146 | 1.00 |

## Fix

Keep every byte until the frame is proven good. On a checksum failure give up
only the start byte and run the same search over what is left:

```cpp
++checksum_failures_;
++rescans_;
discard_front(1);      // the start byte alone, then look again
```

The search skips to the next start byte, so when the byte after the failed start
is not a start byte the extra work is one comparison per byte. When it is, the
next frame is recovered.
