id: E-CPP-0044
title: A lambda that outlived what it captured by reference
match: capturing a container by value copies its buffer
platforms: linux, windows
teaches: 02-08-behaviour-as-a-value
---

## Symptom

A stored callback returns rubbish, or a plausible value that is slightly wrong,
or crashes. It worked when it was called immediately after being created and
stopped working when it was stored and called later.

Under the address sanitizer it is a stack use after return, in a function that
had already returned successfully.

```cpp
std::function<double()> latest_reading() {
  double reading = read_sensor();
  return [&reading]() { return reading; };    // reading dies here
}
```

## Cause

A by reference capture stores somewhere to look. When the thing it looks at is
a local, that somewhere stops being valid as the function returns, and the
callable is left pointing into a stack frame that has been reused.

This is lesson 02-07 with a different shape. There it was a pointer into a
vector that moved; here it is a reference into a scope that ended. The borrowed
thing went away and the borrower did not find out.

**No compiler diagnoses it.** Measured on the function above, with
`-Wall -Wextra -Werror`: gcc accepted it and clang accepted it. The related and
much more obvious case of returning a reference to a local directly is refused
by both, which is in lesson 01-11's checks directory. Hide the same reference
inside a capture list and the diagnostic goes away.

So the most dangerous capture mistake is the one with no diagnostic, which is a
pattern this curriculum keeps running into: the compiler catches the obvious
form and says nothing about the form people actually write.

## Fix

**Capture by value anything that must outlive the scope.** For a stored
callback this is almost always the right answer, and for a `double` it costs
eight bytes.

**Write the precondition down when a reference capture is genuinely what you
want.** "The object this refers to must outlive the returned callable" in a
comment above the signature is the only check there is going to be.

**Be careful what by value costs for a container.** Capturing a
`std::vector` by value copies the buffer: measured, a captured vector of 1024
doubles gave the callable a different buffer from the caller's. And storing
that callable in a `std::function` allocated **3** times, against 0 for one
that captured a single double. Two costs for one capture list.

**Prefer capturing a shared owner over capturing its contents.** A
`std::shared_ptr` captured by value keeps the thing alive and copies a pointer,
which is lesson 02-06, and it answers the lifetime question instead of hoping.

**Run the sanitizer lane.** This is one the address sanitizer does find, at
runtime, on the paths your tests exercise. It is the only tool here that will
tell you.
