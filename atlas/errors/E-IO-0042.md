## Symptom

After the cable goes back in, the first message is missing, and the loss counter jumps
by a large round-looking number a moment later. Both only after a reconnect, so the
bench, which never unplugs, is clean.

## Cause

Reconnecting restores the port and nothing else. Two things hold state from the
connection that is gone.

**A half frame.** The cable was pulled out in the middle of a message, and the parser
is holding the front of it. It is waiting for the rest, and the rest it gets is the
start of the first frame on the new connection. That frame fails its checksum, and
the one after it is the first to arrive whole.

**A counter that restarted.** Unplugging power cycles most devices, and the sequence
number starts again. The tracker expected 9 and got 100, and 100 is a plausible number
for a message that is only 91 ahead, so it counts 91 lost messages that were never
sent.

Measured, the cable pulled out mid frame and put back with the device restarted:

| on reconnecting | sent after | delivered | lost | phantom losses |
|---|---|---|---|---|
| keep the parser and the counter | 17 | 16 | 1 | 91 |
| start both again | 17 | 17 | 0 | 0 |

## Fix

Say that it happened. `generation()` goes up every time a connection is made, and the
code that owns the parser, the sequence tracker, the clock map and a request in flight
compares it with the one it last saw:

```cpp
if (port.generation() != seen) {
  seen = port.generation();
  link.reset(new Link(port, storage, timeout));
  tracker.reset(new SequenceTracker<std::uint8_t>());
  clock_map.reset();
}
```

Everything that learned something from the old connection has to forget it: the
timeline of lesson 08-12 and the request of lesson 08-11 as much as the parser.
