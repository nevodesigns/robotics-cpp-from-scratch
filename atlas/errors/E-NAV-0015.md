## Symptom

A* returns a route that is obviously not the best one, on a map where the better
one is plain to a person looking at it. It happens sometimes and not always, and
the cases that fail look no different from the cases that work.

The search is fast, which is why nobody suspects it.

## Cause

The heuristic overestimates the remaining distance, so A* stops exploring
branches that would have turned out better.

The usual way in is Manhattan distance on a grid that allows diagonal movement:

```cpp
return std::fabs(goal.x - x) + std::fabs(goal.y - y);   // overestimates
```

A diagonal step covers one cell of x and one of y at once, so counting the two
axes separately charges for both. The correct guess discounts the shared part:

```cpp
const double shared = std::min(dx, dy);
return (dx + dy) + (std::sqrt(2.0) - 2.0) * shared;    // octile, admissible
```

Manhattan is larger by `0.586 * min(dx, dy)`, which can be a lot.

Measured over a hundred cluttered maps, against an exhaustive search for the
truth:

| guess | suboptimal on | worst overshoot | cells expanded |
|---|---|---|---|
| octile | 0 of 103 | 0% | 32 686 |
| manhattan | **30 of 103** | 3.45% | 25 368 |

Three maps in ten, by a few percent, for a fifth fewer cells looked at.

Both halves of that are worth stating plainly. It really is faster. It really is
wrong, not rarely and not catastrophically, and on the map you happen to test
first it will probably give the right answer, which is exactly what makes it
survive.

## Fix

Use an admissible heuristic, and be able to say why it is admissible.

The test is simple: the guess must never exceed the true remaining cost. That
follows from the movement model, so write them together and check them together:

```cpp
for (int dx = 0; dx <= 12; ++dx)
  for (int dy = 0; dy <= 12; ++dy)
    RC_CHECK(octile_distance(0, 0, dx, dy) <= dx + dy + 1e-12);
```

The heuristic and the step cost are one design, not two. Diagonals allowed at
`sqrt(2)` means octile. Diagonals forbidden means Manhattan is correct and
octile is now the one that underestimates, which is safe but slower. Change one
and the other is wrong.

If a suboptimal answer really is acceptable in exchange for the speed, say so
where the option lives, name the amount you measured, and keep an admissible
search alongside so the trade can be re-measured when the maps change. A
deliberate 3 percent is engineering. An accidental 3 percent is a bug that
happens to be small this week.
