## Symptom

Objects held by std::shared_ptr are never destroyed, even after every visible
handle has gone out of scope. Destructors that should log or release hardware
never run. A leak checker reports the blocks as still reachable.

## Cause

Two objects hold shared_ptr to each other, directly or around a longer loop. A
shared_ptr releases its object when its count reaches zero, and inside a cycle
each one is kept alive by the other, so neither count ever reaches zero.

The classic shape is a tree where each node owns its children and every child
also holds a shared_ptr back to its parent.

## Fix

Decide which direction owns, and make the other direction non owning.

```cpp
std::vector<std::shared_ptr<Node>> children_;   // owns
std::weak_ptr<Node> parent_;                    // observes
```

A weak_ptr does not contribute to the count. Ask it for a usable pointer with
lock(), which answers null when the object has already gone, so the caller has
to handle the case where the parent no longer exists rather than assuming.

Before reaching for weak_ptr, ask whether shared ownership was needed at all.
Most trees have exactly one owner and can use unique_ptr for children and a plain
non owning pointer for the parent link.
