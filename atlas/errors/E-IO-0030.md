id: E-IO-0030
title: A drain with no limit, or with a buffer that is too small
match: a device that never stops cannot hold the loop
match: a message too big for the buffer is not copied and cannot overrun it
platforms: linux, windows
teaches: 08-09-the-newest-reading-or-all-of-them
---

## Symptom

The control loop misses its deadline when the device is busiest, which is when it
matters most. Or a fault appears in code far from the read, a corrupted local
variable or a crash after the link is told to send a large message.

## Cause

Two ways a drain turns into its own bug.

**No limit.** `while (link.poll(now))` runs until nothing is waiting. A device that
sends as fast as the loop can read, or faster, means nothing is ever waiting, and
the call does not return. Every other job in the loop, including the one that
stops the robot, waits for it. A loop has a deadline, and a call that can take as
long as the device chooses does not belong in it.

**No size check on the copy.** The newest message is copied out of the link
because the link's own view is only good until the next poll. A message larger than
the destination, copied without checking, writes past the end of it.

## Fix

Bound the call and check the copy:

```cpp
while (taken < limit && link.poll(now)) {
  ++taken;
  if (message.size() > out.size()) { ++result.oversized; continue; }
  ...
}
result.more = limit != 0 && taken == limit;
```

`more` says the drain stopped because of the limit, so the caller can decide
whether to come back at once or let the next tick do it. Measured, with two hundred
thousand frames waiting and a limit of 64, the call returned having taken 64, and
nearly all of the rest was still waiting.
