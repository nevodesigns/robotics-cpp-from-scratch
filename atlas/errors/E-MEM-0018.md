title: The recursion that ended the program
match: (Segmentation fault|stack overflow|status 139|signal 11)
platforms: linux, windows

## Symptom

A program that works on small input dies on large input. No exception, no
error message, no last line of output.

```
$ ./plan_route big_map.csv
Segmentation fault (core dumped)
$ echo $?
139
```

Often it is intermittent in a way that looks like data corruption: the same
map works today and fails tomorrow, because the depth it reaches depends on
the shape of the input rather than its size.

## Cause

The stack ran out.

Locals live in a region whose size is a **setting**, not a property of C++.
Measured on this curriculum's machine: 8192 KiB, which `ulimit -s` prints.
Windows fixes it at link time instead, with a default of **1 MiB**, so a
recursion that is comfortable on Linux can end the same program on Windows.

Each call takes a frame. Measured: a small recursive function reached depth
**130860** before dying with signal 11, and 8 MiB over 130860 frames is **64
bytes a frame**. So the depth you can afford is the limit divided by the
frame, and a frame holding a 1 KiB buffer buys about 5000 levels rather than
130000.

`139` is not an exit code the program chose. Lesson 00-09 has the arithmetic:
128 plus the signal, and 11 is `SIGSEGV`. It also explains the missing last
line of output, which was still in `stdout`'s buffer when the process died.

Two related ways to run out without recursing at all.

**A large local costs its space on paths that never run it.** The frame is
allocated when the function is entered, not when the declaration is reached.
Measured: a 15625 KiB array declared in `main` crashed the program on a branch
that only used a `std::vector` and never touched the array. Moving the array
into its own function made that branch survive.

**A variable length array** puts a runtime sized object on the stack, and both
gcc and clang accept one **silently** under `-Wall -Wextra`. It is not
standard C++; it is a C99 feature both offer as an extension.

## Fix

Give the recursion a limit it can report against, so deep input produces a
partial answer rather than a signal.

```cpp
#include <rc/core/recursion.hpp>

bool visit(const Node& node, rc::core::DepthLimit& limit) {
  const rc::core::DepthGuard guard(limit);
  if (!guard.ok()) return false;        // too deep: say so, do not recurse
  for (const Node& child : node.children)
    if (!visit(child, limit)) return false;
  return true;
}
```

Then choose the limit from the arithmetic rather than from a round number:

```cpp
const int limit = rc::core::depth_that_fits(8L * 1024 * 1024, 64);   // 87381
```

Two thirds of the quotient, because the frame you measured is one function and
the real call chain includes everything it calls.

The decrement is a destructor, not a line at the bottom of the function, for
lesson 02-03's reason: an early return skips a line and skips no destructor,
and a depth counter that leaks reports a limit that was never reached.

Three further moves, in the order they are usually worth it.

**Turn the recursion into a loop with an explicit stack.** A `std::vector` of
pending nodes grows on the heap, which is large, and the depth becomes a
number you can print rather than a frame count you cannot.

**Switch `-Wvla` on**, or `-pedantic-errors`. Both compilers reject a variable
length array with either, and both are silent without. This is lesson 04-08's
subject.

**Move large locals to the heap**, or into their own function if they must be
locals, so they do not cost their space on every path through the caller.
