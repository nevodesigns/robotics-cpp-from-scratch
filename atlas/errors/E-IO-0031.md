title: Reading on the thread that also does the work
match: while the main thread is busy for longer than the buffer lasts, a reader thread loses nothing

platforms: linux, windows

## Symptom

Messages go missing in bursts when the program does something slow: a save, a
redraw, a log flush, a network call. The loss is bigger the slower the thing is.
A faster computer helps and does not cure it, because the cure is not speed.

## Cause

The reading shares a thread with everything else the program does, so the stall
budget from lesson 08-08 is spent by all of it. The buffer is 4096 bytes and the
device is sending 1000 frames a second: 372 ms. Anything on that thread that takes
longer than 372 ms, by any route, loses frames, and the code that did it has no
way to know.

Measured, a main thread that did nothing for 900 ms with the device sending 1000
frames a second:

| reading | frames lost | bytes dropped |
|---|---|---|
| on the main thread | 628 | 6904 |
| on a reader thread | 0 | 0 |

The 628 is not noise: the buffer holds 372 frames, the stall was longer than the
time it takes to fill, and everything after that was dropped. The reader thread
did nothing but look at the port, and its longest gap between looks was 0.8 ms
against a budget of 372 ms.

## Fix

Give the reading a thread of its own, and hand what it reads to the rest of the
program through something built for it: a `Seqlock` for the newest, a queue for
every message. Then the budget can only be spent by the reader's own code, which
is a loop with no work in it.

The reader's own gap is worth exposing. `longest_gap_us()` is the number to compare
with the budget, and a reader that is being starved by the machine shows it.
