title: Five special members written by hand that drift apart
match: declaring all five is correct and is not the advice
platforms: linux, windows

## Symptom

A class has a destructor, a copy constructor, a copy assignment, a move
constructor and a move assignment, all written out, and one of them is subtly
different from the others. A member added last month is copied by the copy
constructor and not by the copy assignment. Self assignment leaves an object
empty. A moved from object is left in a state the destructor does not expect.

Every one of those is a bug lesson 02-05 had you write the operations by hand
specifically to meet.

## Cause

The five operations have to agree with each other, and with the member list,
and nothing checks that they do.

Lesson 02-05 wrote them out once on purpose, so that what a resource owning
type has to get right is something you have done rather than read about. The
conclusion of that exercise is not that you should keep doing it.

Measured, a class with all five written `= default` behaves identically to one
that declared nothing: the same trait, the same buffer travelling on a move,
and the same 71 allocations growing a container. It cost six lines, and those
six lines now have to stay correct as the class changes.

The class that declared nothing has nothing to keep in step with anything. Add
a member and all five adjust.

## Fix

**Prefer the rule of zero.** Hold members that look after themselves, declare
none of the five, and the compiler writes all of them correctly, for ever, as
the class changes.

**When you genuinely need one, use `= default` for the rest.** Six lines of
`= default` is much better than six hand written bodies, and it keeps the
behaviour the compiler would have given you.

**Write them out by hand only when the class owns a raw resource**, which is a
file descriptor, a device handle, a C API object, or memory from `malloc`.
There the rule of five applies, and `rc/core/buffer.hpp` from lesson 02-05 is
what that looks like.

**Or wrap the raw resource once and go back to zero.** A `std::unique_ptr` with
a custom deleter, or a small RAII handle like `rc/io/handle.hpp` from lesson
02-03, owns the awkward thing, and every class built on top of it declares
nothing again. That is almost always the better shape: one type that knows
about the resource, and everything else written in the easy style.

**Check self assignment if you do write them.** `a = a` is the case hand
written assignment gets wrong most often, and lesson 02-05 has the test for it.
