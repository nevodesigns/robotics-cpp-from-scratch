id: E-MEM-0019
title: A loop over something that was already gone
match: (stack-use-after-scope|temporary in the range expression)
platforms: linux, windows
teaches: 01-16-the-loop-variable-is-a-copy
---

## Symptom

A loop over the result of a function call produces a wrong total, or garbage,
or occasionally works. There is no crash and no error in a normal build.

```
$ ./plan
sum = 2882482050
```

Under the address sanitizer:

```
ERROR: AddressSanitizer: stack-use-after-scope on address 0x7ffd...
READ of size 8 at 0x7ffd... thread T0
```

## Cause

In a range based for, the thing after the colon is evaluated **once**, and a
temporary inside it that is not the final result is destroyed before the body
runs.

```cpp
for (int x : Holder().items()) { ... }     // items() returns a reference into the Holder
```

`Holder()` is a temporary. `items()` hands back a reference into it. The loop
keeps the reference and the temporary is gone.

Measured with a counter of destroyed holders: when the body first ran the
count was **1** for a temporary and **0** for a named object. If the function
returns a copy, by value, the copy is kept alive for the loop, so only a
reference into the dead object is the problem.

Run once outside the test suite, the dangling version summed to
**2882482050** with no error. That is a read of memory that had been the
holder's, and it looked like a number.

C++23 changed this rule so that all temporaries in the range expression live
for the whole loop. This curriculum is on C++17, where they do not.

## Fix

Give the loop something that outlives it.

```cpp
const Holder holder;                         // a name, so it lives
for (int x : holder.items()) { ... }
```

or return by value from the function being called:

```cpp
for (int x : make_holder().items_by_value()) { ... }   // the copy is kept
```

The address sanitizer finds this on the paths a test runs, which is a reason
to run the loop in a test with the sanitizer lane on.
