## Symptom

Adding threads makes the program slower. Two threads counting their own events
into their own variables run several times slower than one thread doing both
jobs, and nothing is shared between them: no lock, no queue, no common data.

Profilers point at the increment, which is one instruction.

## Cause

Caches do not move bytes, they move lines, and a line is 64 bytes. Two variables
in the same line are one thing as far as the hardware is concerned: each write
by one core takes the line away from the other.

Two atomic counters, two threads, four million increments each:

| bytes between them | ms | relative |
|---|---|---|
| 8 | 159.0 | 1.00 |
| 16 | 139.1 | 0.88 |
| **64** | **27.1** | **0.17** |
| 128 | 27.8 | 0.18 |

Nothing changes until the two cross a line boundary, and then everything does.
Six times, from moving one variable.

The most common way to write this is the most natural code there is: an array
with one slot per thread.

| four threads, four million increments each | ms | relative |
|---|---|---|
| `std::vector<std::atomic<long>>`, one per thread | 162.1 | 1.00 |
| the same, one slot per cache line | 34.8 | 0.21 |
| a local on the stack, published once | 7.6 | 0.05 |

Every slot in that vector is eight bytes, so all four live in one line, and four
cores fight over it for the whole run.

## Fix

In order of how much they buy.

**Do not share the line at all.** Accumulate in a local and publish once at the
end. The stack is per thread by construction and the counter is never contended.
That was twenty one times faster than the packed array and five times faster
than padding it, and it is usually available.

**Give each hot value its own line** where it must be shared as it changes:

```cpp
std::vector<rc::rt::Padded<std::atomic<long>>> slots(threads);
```

`alignas` on the type rather than on a member, so the padding survives being put
in an array. That is the difference between `sizeof` being 64 and the vector
packing eight of them into one line anyway.

**Know what it costs.** A padded counter is 64 bytes instead of 8. For a handful
of per-thread values that is nothing; for a million objects it is eight times the
memory and a different problem. Pad the few things that are written by more than
one thread, not everything.

C++17 named the distance `std::hardware_destructive_interference_size`. The
standard library on Ubuntu 22.04 does not provide it, so this curriculum uses a
constant with a measurement behind it, and the test sweeps the distance rather
than trusting either.
